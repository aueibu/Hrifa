Kit tokens in section 5 are measurements of the lab; where a token is marked decided it supersedes the lab value. Section 7 lists the questions and the answers. Nothing in this folder is code yet. Colours follow `src/theme/THEMING.md` (roles such as `--panel`, `--text-muted`, `--mark-<hue>`; no hex, no palette shades).

## 1. Vocabulary

- **Region**: a permanent part of the screen. Today there are two: the **Inspector** (left; its content follows what is selected) and the **Stage** (centre). A region is not a module and is not arranged by the user.
- **Module**: a self-contained view with an id and a title: piano roll, desk/canvas, chord picker, lineage graph, a lab panel. A module is written once and knows nothing about where it is shown.
- **Slot**: a named place on the Stage that holds one module at a time. Slots stack and move; a module in a slot is mounted once (section 3).
- **Layout**: the arrangement of slots (which modules, in which columns and stacks, with which splitter shares). Plain serialisable data with a version field; it holds module ids and numbers, never components.
- **Size**: the proportions of the room a slot gives its module, as a named class along each axis (width: `narrow` / `regular` / `wide`; height: `short` / `regular` / `tall`), measured from the slot itself and never from the window. A module declares the sizes it supports and renders differently per size, the way it already renders for light and dark. It never learns where it sits. ("Size" was chosen over "shape" by the human, 2026-11-13.)

A region contains slots. A slot contains one module. A layout lists the slots. A size is given to the module by the slot.

## 2. Size classes

Two independent axes. A module receives `{ width, height }`, for example `{ width: 'wide', height: 'short' }`. It never receives pixels.

### Measurement rule

The size is measured on the **slot body**: the area below the slot's header strip, border-box (padding included), by a `ResizeObserver` on that element. The window is never consulted. The slot publishes the result as a hook value and as `data-slot-size="<width>-<height>"` on the slot body so CSS can switch on it. Thresholds are named tokens defined once (in `src/lib/stage/`, M2), in rem, compared against the measured width converted to rem.

### Scale (decided 2026-11-13, STAGE-4)

One scale on both axes, in multiples of a base unit. The unit applies to slot sizes only, not to control sizes (rows, paddings and splitters keep the lab's measurements, section 5).

| token                | value                      | reason                                                                                                                                                                                                                            |
| -------------------- | -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SIZE_UNIT_REM`      | 6                          | The base unit. It is also the smallest slot height, the lab's `SPLIT_MIN_REM = 6` (`harmonic-field-lab/state/layout.ts:327`).                                                                                                     |
| nominal sizes        | 4U, 6U, 8U = 24, 36, 48rem | The size each class is designed around. 24rem is one lab pinned column (`lab.module.css:21`, `COLUMN_REM = 24.25` with its gap, `layout.ts:72`) and about half a column's height on a typical screen (an estimate, not measured). |
| `SIZE_SMALL_MAX_REM` | 30 (5U)                    | Boundary between `narrow`/`short` and `regular`. Midway between the nominal 24 and 36.                                                                                                                                            |
| `SIZE_LARGE_MIN_REM` | 42 (7U)                    | Boundary between `regular` and `wide`/`tall`. Midway between the nominal 36 and 48.                                                                                                                                               |

| axis   | small                 | middle                       | large                   |
| ------ | --------------------- | ---------------------------- | ----------------------- |
| width  | `narrow`: below 30rem | `regular`: 30 to under 42rem | `wide`: 42rem and above |
| height | `short`: below 30rem  | `regular`: 30 to under 42rem | `tall`: 42rem and above |

Where today's code lands on the scale: the lab column (24rem) is `narrow`, and so is its 20rem form below 70em (`lab.module.css:64-66`); the chord dock's default width (30rem, `DEFAULT_CHORD_DOCK_WIDTH = 480` px, `composition-workbench/noteEditorPreferences.ts:49`, W-17) sits exactly on the boundary and counts as `regular`; a stacked lab panel at its minimum is 1U high. The 30 and 42rem boundaries are the human's choice, not anchored in code. Three tiers per axis is common practice (Mantine's `xs` and `sm` breakpoints are 36em and 48em; Material's window size classes use three tiers; both quoted from memory, not verified), and breakpoints are best set from what the content needs rather than from devices, which is why the thresholds are tokens.

The dock's effective maximum is 60% of the width of the panel it sits in, or 960 px when that is unknown (`FALLBACK_MAX_WIDTH`, `ChordPickerHost.tsx:20,76-78`); `MAX_CHORD_DOCK_WIDTH = 1600` is only the clamp applied when the preference is stored (`noteEditorPreferences.ts:143,174`). Neither needs a size class of its own.

### Minimum slot

2U wide by 1U high, 12rem by 6rem (`SIZE_MIN_WIDTH_REM = 12`, `SIZE_MIN_HEIGHT_REM = 6`), the height **including the 1.875rem header strip** (`lab.module.css:316`), so the slot body, which is what the size is measured on, is at least about 4.1rem high. The chord dock's own minimum is 14rem (`MIN_CHORD_DOCK_WIDTH = 224` px, `noteEditorPreferences.ts:48`); the Stage minimum is a little narrower and replaces it when the dock moves onto the Stage. The workbench's stage split uses a share (`MIN_SPLIT = 0.2`, `MAX_SPLIT = 0.8`, `SplitStage.tsx:6-7`), not a rem figure; the Stage uses the lab's rule (the larger of 6rem and 20% of the column, `SPLIT_MIN_SHARE = 0.2`, `layout.ts:325-327`).

### Hysteresis

A size class changes only when the measured value crosses a threshold by more than 0.5rem back the other way, so a splitter drag that hovers on a boundary does not make the module flicker between two renderings. (Decided 2026-11-13, Q4.)

### What a module does at its minimum size

At `narrow`/`short` (about 12rem by 4.1rem of body) a module must still:

1. show its title or a one-line summary of its state (the header strip shows the title; the body may show a value);
2. never overflow the slot: no horizontal page scroll, no clipped controls; extra content scrolls inside the module's own body (the lab does this: `.panelBody` has `overflow-y: auto; overflow-x: hidden`, `components/panels.module.css:4-18`);
3. keep every control reachable (by scroll or by a menu), dropping labels and secondary readouts before dropping controls;
4. keep its state; shrinking is never a reason to unmount.

If a module cannot do that, its `minSize` says so and the layout refuses to give it less (section 3).

## 3. Module contract

```ts
interface StageModule {
  id: string; // unique, stable, never reused; persisted in layouts
  title: string; // shown in the slot's header strip
  sizes: SizeSet; // the size classes it has a rendering for
  minSize: Size; // the smallest room it will accept
  render(size: Size): ReactNode;
}
```

The registry is an **open set of ids**: `createRegistry(metas)` builds it from data-only `ModuleMeta` (`{ id, title, sizes, minSize }`; the React `render` function is attached in `src/pages/stage/`, M3), and a layout may name any registered id. There is no `PanelId` union (the lab has one, `harmonic-field-lab/state/layout.ts`; see section 6). A stored layout naming an id that is not registered loads without it and never throws.

`sizes` is the set of classes the module has a deliberate rendering for. If the slot's measured size is not in the set, the slot passes the nearest supported size (the largest supported that fits, else the smallest supported) and the module is shown in that rendering with the leftover room as padding or scroll, never stretched in a way the module did not design for. `minSize` is the smallest `{ width, height }` the slot may be given; a move, stack or splitter drag that would go below it is refused or clamped.

### What a module may NOT do

- Read the layout, or know which column, side or stack position it is in.
- Assume a pixel width or height. It reads `size` only.
- Reach into its parent (query `parentElement`, measure it, or portal into an ancestor it was not given). The workbench's chord picker host does exactly this today: it reads `frameRef.current?.parentElement` and watches it with a `ResizeObserver` to limit the dock's width (`ChordPickerHost.tsx:60-73`); a Stage module has no such back door. If a module needs a bigger room it asks for a different slot through the Stage, not by reaching.
- Open its own floating window or free-positioned panel. The only floating element a module may use is a transient popover anchored to its own control (a Mantine `Menu`, `Popover` or `Tooltip`), as the lab's header menus do (`components/Panels.tsx`, the Stack menu).
- Persist its own position or size. The layout does.

### Mounted-once rule (moving keeps state)

A module instance is created once per slot id and **never unmounted by a move, stack, unstack or reorder**. The Stage keeps one stable React element per module id, keyed by the module id (not by column or index), and moves it between slots. A mechanism that can satisfy this in React is a portal into the slot's body element, created once per module and retargeted on a move; re-keying by position would remount the module and lose its state. Nothing today meets this rule: `ChordPickerHost` portals into the takeover slot (`useCanvasTakeoverElement()`, `ChordPickerHost.tsx:49-50`; `createPortal(frame, slot)`, `:172-174`) but switching between dock and takeover changes the element tree (a portal versus a fragment with splitter and frame), so the body remounts. It is not a precedent.

Why: a move is a change of room, not a change of content. A chord picker with a half-typed filter, a roll with its scroll and zoom, a text field with an uncommitted edit must survive being dragged from the side column to the top. This is also what makes the lock-in fear go away: arrangement is data and costs the module nothing. (Closing a module is the only action that unmounts it, and then its state is dropped on purpose.) A test in M3 and M5 asserts this for the chord stand-in.

The one exception that is not an exception: the module's **rendering** may differ per size (a different tree), but its **state** lives above the render function (in the module's own component, keyed by id), so a size change keeps the filter, selection and scroll that make sense in both renderings. A module author is responsible for keeping state out of the per-size branch.

## 4. Worked examples

### 4a. Chord picker: one body, two sizes

Today (the workbench, W-16/W-17): `ChordPickerHost` (`composition-workbench/chordInput/ChordPickerHost.tsx`) frames one `ChordPicker` body in one of two named slots, a fixed-width **dock** beside the roll (default 30rem = 480 px, min 14rem = 224 px, max 60% of the panel it sits in (960 px when unknown; the stored preference is clamped to 1600 px); draggable splitter with arrow-key nudges of 16 px, `KEY_STEP = 16`, `ChordPickerHost.tsx:19`) or the **canvas takeover** over the desk area. The body takes no host-specific props ("The body (ChordPicker) is the same in both and takes no host-specific props", `ChordPickerHost.tsx:27-29`), and the dock width and host are per-viewer prefs `chordDockWidth` and `chordHost` (W-10, W-17). The size is implied by which slot it is in, and the host knows it. That is the thing the Stage generalises: the body learns its size from the slot instead of the host choosing a frame.

On the Stage, one chord picker module with these renderings:

| slot size                                         | where it typically sits       | rendering                                                                                                                              |
| ------------------------------------------------- | ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `narrow` x `tall` (12 to under 30rem wide)        | a column beside the roll      | one column of chord buttons, single role at a time (the role selector), the label strip collapsed to a one-line current-chord summary. |
| `regular` x `tall` (30 to under 42rem wide)       | the default dock (30rem)      | today's dock rendering: the common-tone columns with sideways scroll below a minimum column width (W-19).                              |
| `wide` x `short` (42rem and up, under 30rem tall) | above the roll                | a horizontal strip: roles as columns side by side, one row of chord buttons per role, scrolling sideways, no stacked rows.             |
| `wide` x `tall`                                   | the takeover, or a large slot | all roles as columns, every tier of chords visible (the takeover's rendering today).                                                   |

All four are one component (`render(size)` branches on `size`), the filter, the anchor, the selected chord and the keyboard state are held outside the branch, and moving the module from beside the roll to above it changes only the `size` argument. The picker's keyboard flow (W-20) is attached to the module, not to a position.

### 4b. Piano roll

The module wraps the shared `PianoRoll` (`components/PianoRoll/PianoRoll.tsx`), consumed only through its props. Props that matter for sizing: `fill` (the roll takes the full width and height its parent gives, `PianoRollProps.fill`), `detachedScroll` (one panel: keys outside the scroller, lane slot, one scrollbar), `showToolbar` (hide the zoom and follow controls), `height` (a fixed height when not in `fill`), `view`/`onViewChange` (the owner holds scroll and zoom, so they survive moves), `lane` (a velocity lane slot), `tools`/`actions`/`activeTool` (the palette), and the opt-in chord overlay props (`ghostNotes`, `onAnchorClick`, `onAnchorHover`, W-15 to W-18).

What it shows per size (proposed; all rendered with the same `view` state):

| slot size                    | rendering                                                                                                                                                                                                      |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `wide` x `tall`              | full unified panel: `fill`, `detachedScroll`, toolbar, tool palette, velocity lane under the roll.                                                                                                             |
| `wide` x `regular`           | `fill`, `detachedScroll`, toolbar and palette; the velocity lane is hidden (it is the first thing dropped).                                                                                                    |
| `regular` x any              | `fill`, palette collapsed to a narrow set of tools; toolbar hidden (`showToolbar={false}`), view set by the owner.                                                                                             |
| `narrow` x any, or `short`   | `fill`, a read-and-select roll: no palette, no lane, no toolbar; editing still works by keyboard.                                                                                                              |
| minimum (`narrow` x `short`) | a compact roll with no toolbar, palette or lane, enough to see the notes under the playhead. (Hiding the keyboard column as well would need a new `PianoRoll` prop: out of this arc's scope, so not proposed.) |

These are proposals for M5; M1 only fixes the idea that one module renders those variants from one `view` state. `PianoRoll` is not changed by this arc.

## 6. Gap list

### What the lab's layout does not do that the Stage needs

- **No size awareness.** The lab chooses between layouts by window width only (`fitColumns(widthRem)`, `state/layout.ts:77-83`, and the `@media (max-width: 70em)` rule, `lab.module.css:64`). No panel receives a size; each panel is built for 24rem. The Stage adds a per-slot `ResizeObserver` and the module-size contract.
- **Hardcoded `PanelId` union.** Panels, their labels (`panelLabel`), their render switch (`Panels.tsx:45`) and their default views are keyed to a closed union in `state/layout.ts`. The Stage needs an open registry of ids with a parser that drops unknown ids.
- **Page-local.** `state/layout.ts`, `Panels.tsx` and `ui.tsx` live inside the lab and import its state context (`useLab`, `useViz`, `ui.tsx:132`) and glossary (`TIPS`). Nothing outside the lab can use them; the kit's `Strip`, `Row`, `Num` are generic but are wired to `PinActionsContext` and the lab's tip texts. The Stage's kit has to be page-independent.
- **No shared components.** `Strip`, `Row`, `Num`, `Tip`, `CommitNumber`, `DebouncedText` are not in `src/components/`; the workbench re-implements the same ideas separately. Promotion is M6.
- **Fixed column model.** Columns are 24rem wide, one to three panels each (`MAX_STACK = 3`, `state/layout.ts:86`); there are no variable widths and no per-column minimum other than the fit rule. Decided (Q12): the Stage makes column widths adjustable (stored in the layout).
- **No size-driven restructuring inside a panel.** A panel with a two-column cluster grid (`.clusters`, `panels.module.css:709`) has no narrow rendering.
- **No mounted-once guarantee for moves.** The lab remounts a panel when it changes column (its panels are re-rendered from the layout); the Stage needs the keyed, portal-based rule in section 3.
- **Splitters are vertical only** (between stacked panels); the Stage's splitters are the same idea (small adjustments, pointer and keyboard), and column-width splitters are not in the lab at all. Decided (Q12): the Stage has column-width splitters as well as the vertical stack splitters.

- **`SplitStage`** (`composition-workbench/components/SplitStage.tsx`): a hardcoded vertical split of canvas above and bottom panel below, share clamped 0.2 to 0.8, 1rem grip with a 3px handle, keyboard support. One fixed arrangement, not a layout.

## 9. Layout core (M2)

The pure layout code lives in `src/lib/stage/` (README there has the full API). Summary of the rules the React layer relies on:

- `Layout = { version: 1, columns: Column[] }`; a `Column` is `{ slots: string[] (1 to 3, top first), width?: rem (default 36, clamped 12 to 96), shares?: number[] (sum 1, default even) }`. One ordered row of columns: the lab's left and right sides are dropped.
- Size tokens and classification (`classifyWidth`, `sizeOf` with the 0.5rem hysteresis, `nearestSupportedSize`, `slotSizeAttr`) are in `size.ts`. Hysteresis: a class below a boundary B moves up only at B + 0.5, a class above B moves down only below B - 0.5.
- Operations never mutate and return the same object when they do nothing; changing a column's slots drops its shares.
- Two splitter kinds: vertical stack shares (each slot at least the larger of 6rem and 20%) and column-width splitters (the two neighbours trade width, total constant, both within 12 to 96rem).
- `fitColumns` keeps whole columns left to right and stops at the first that does not fit; the rest are hidden but stay in the layout.
- `parseLayout(raw, known)` never throws and drops unknown ids, repeats, empty columns and bad shares; the storage key is `hrifa.stage.layout.v1` (the page does the storage access).
- `nearestSupportedSize` tie-break: "largest" means highest width index plus height index; ties go to the wider size.
- `unstack` gives the new column the default width. `fitColumns` can return 0, so M3 must show at least one column. `parseLayout` renormalises stored shares within 0.02 of summing to 1 and drops the rest; it takes a `fallback` layout (M3 passes the real default columns).
- `minSize` is not enforced by the M2 core; the Stage enforces it in M3 (section 10).

### How size flows

`ResizeObserver` on the slot **body** (border-box, header excluded) -> `Slot` reads `getBoundingClientRect()` and converts px to rem with the document root font size -> `onMeasure(id, widthRem, heightRem)` -> `Stage` folds it into `sizes[id]` with `withMeasure` (`sizeOf` with the 0.5rem hysteresis against the previous class) -> `data-slot-size="<width>-<height>"` on the body gets the measured class, and the module's `render(size)` gets `nearestSupportedSize(measured, module.sizes)`. A slot that is not laid out (a zero rectangle, e.g. a hidden column) keeps its last size. Until the first measurement a module is rendered at `regular x regular`.

### Mounted-once mechanism and its limits

Each module in the layout is rendered **once**, at the Stage root, in a list keyed by module id: `createPortal(module.render(size), hostElement, id)`. `hostElement` is a persistent `div` the Stage creates per module id (kept in a ref, never re-created while the module is in the layout). A `Slot` adopts it in a layout effect (`body.appendChild(host)`) and releases it on unmount only if it is still the parent. So a move, stack, unstack, reorder or resize changes where the host hangs in the document and never the React element that owns the module's state; hidden columns stay mounted (their hosts are detached). Closing a module (removing it from the layout) unmounts it and drops its host.

Known limits:

- Reparenting a DOM node loses keyboard focus and the scroll position of scrollable descendants. Restored: (a) focus inside the module (the old slot records the focused element in a `WeakMap` keyed by the host before releasing it, the new slot refocuses it after adopting); (b) after a slot tool moved the slot (left, right, up, down, stack, unstack) focus goes to the same tool, found by its accessible name, in the module's new slot, or to the slot section when that tool is disabled or gone (the Stage does this in a layout effect after the layout update; the intent expires after 1 s so a refused action never steals focus later). NOT restored: scroll positions (a module that cares keeps its scroll in state, like the roll's `view`), text selections, playing media.
- Anything a module renders into a portal of its own (Mantine menus, tooltips) is unaffected. React events from the module bubble through the React tree (the Stage), not the DOM position.
- Hidden columns are mounted but have no measured size, and keep rendering at the last size.

### minSize

A module's `minSize` is a size class read as a floor in rem (width: narrow 12, regular 30, wide 42; height: short 6, regular 30, tall 42; the scale boundaries; height includes the header strip). Enforced in `stageOps.ts`:

- **Refused**: a move, stack or unstack that would leave a slot below its module's minimum returns the layout unchanged (`guarded`; a slot that was already below before the change does not block it). The matching tool is shown disabled (a Stack menu item for a column too narrow, a greyed move button). Heights are only checked once the stage height is known.
- **Clamped**: the column width splitter (drag, arrows, Home, End) stops at the minimum widths of the modules in its two columns, and a stack splitter stops where either slot would drop below its module's minimum height (header included; `stackSplitterBounds`). Both report the real limits in `aria-valuemin` and `aria-valuemax`. If the two minimums cannot both fit, the splitter does nothing.
- **Widened**: a module added from the Modules menu or unstacked gets its new column widened to its minimum width.
- A module can still end up below its minimum only when the window forces it (a first column wider than the window scrolls instead of shrinking).

### Behaviour of the pieces

- Visible columns: `shownColumnCount(layout, widthRem)` (in `stageOps.ts`, used by both `Stage` and `StageApp`) is the longest left-to-right prefix whose widths, 0.5rem per splitter between columns and the 0.5rem stage padding fit the window, at least one and at most the number of columns (it does not use the core's `fitColumns`, whose per-column gap is 0.25rem); the first column may overflow and the column strip scrolls sideways. Hidden columns stay in the layout and are listed in the top bar "Hidden columns" menu; choosing one moves its column to the front (`moveToFront`). A splitter sits only between two visible columns.
- Splitters: `aria-orientation`, `aria-valuenow`, `aria-valuemin/max`; keyboard (column: Left/Right 1rem, Home/End; stack: Up/Down 5%, Home/End); pointer drag. The column index is looked up when the action runs (by module id), never cached. After the stage height is measured `clampColumnShares` repairs stored shares below the minimum.
- Slot tools: move left, move right, (in a stack) move up and down, stack onto (a menu of `stackTargets`), unstack, close. All are buttons with accessible names.
- Persistence: key `hrifa.stage.layout.v1` (`LAYOUT_STORAGE_KEY`), loaded with `parseLayout(raw, registry, fallback)` where the fallback is `DEFAULT_STAGE_LAYOUT` (a picker column and a roll-over-notes stack), saved on every change in try/catch. "Reset layout" restores the default. The only other key is `hrifa.stage.tipDelay.v1` (the developer option, section 11); no other key is read or written.
- Column width comes from the layout (rem, default 36); the window width only decides how many columns are shown. The stage fills the height under the 40px top bar.

### How to add a module (recipe)

1. Write the module as a component that takes `size: SlotSize` and nothing else. Keep state above the per-size branch (in the component), never in the branch.
2. Add an entry to a registry list: `{ id, title, sizes, minSize, render: (size) => <MyModule size={size} /> }` (`standins/index.tsx` is the example). `id` is unique and stable (it is persisted). `sizes` lists the classes it has a rendering for (each at least `minSize`; `registryProblems` in the core checks this). Pick `minSize` as the smallest room it still works in.
3. Build the registry once at module scope with `createStageRegistry` and pass it to `<Stage registry layout update widthRem />`. A module appears on the Stage when its id is in the layout: add it to a default layout or from a menu (`addWithMin`).
4. Do not read the layout, query a parent or assume pixels (section 3). If it cannot work at its minimum size, raise `minSize`.

## 11. Inspector kit (M4)

`kit/` holds thin Mantine wrappers with fixed sizes (`Kit.tsx`), the token table (`tokens.ts`), the developer option (`settings.ts`) and the demo (`KitDemo.tsx`, the "Kit demo" module in the Modules menu: one panel at each density). Import from `kit/index.ts`.

### Density: one token set

`tokens.ts` defines every kit size once. A density is a complete set (`DENSITY_TOKENS`); `KitScope density="compact"` writes it as `--kit-*` custom properties and every rule in `kit.module.css` reads them. Colours are theme roles only. `compact` is the lab's measurement (section 5a, Q8); `roomy` (about 1.15x) is a proposal so the setting can be seen working; both are to be honed at the M5 checkpoint. Sizes that do not change with density (field widths, tooltip width, strip title weight) are `FIXED_TOKENS`. Nest `KitScope` to show another density; there is no global density switch yet.

### How to add a panel

1. Wrap the inspector region once in `<KitScope density=...>`. A panel is `<Panel title tools>`: a header strip over a scrolling body.
2. Body, top to bottom: `Section`s (inset group, heading, optional `aside`), each holding `Row`s; then at most one `Actions` row.
3. A `Row` is `name` (muted, left) and a value (right). The value is a `Num` for a read-out, or exactly one field: `TextField`, `NumberField` (4 rem, `wide` 4.5 rem), `SelectField` (6.875 rem, or `fill`), `SegmentedField` (give the row `fill`). The name labels the field, so fields in rows need no label of their own; outside a row pass `aria-label`. Every row is one row height (`--kit-row-height`, 1.625 rem in compact), whatever it holds, so rows line up down the panel.
4. On/off is `Toggle` only (a pressed button, accent fill while on). Its label is one or two words ("Active"); longer meaning goes in a `Tip` around it (`as="control"`), never in the label. There is no switch and no checkbox in the kit.
5. Fixed (do not override at the call site): input height, font sizes, paddings, gaps, radius, strip height, field widths, tooltip (300 wide, on top, open delay from the developer option). If a panel needs a different size, change the token table, not the panel.
6. Where actions go: view tools (pin, close, collapse, anything about the panel as a view) are `StripTool`s in the strip, right side, subtle gray icons with a required label. The panel's commands (Apply, Reset, Add) are `ActionButton`s inside one `Actions` row at the end of the body, right-aligned, the primary one last. A command that belongs to one section may sit in that section's `aside`. Never put a command in a `Row`.
7. Terms that need explaining use `Tip term text`. Colour comes from roles in the kit's CSS; a panel adds no colour of its own.

### Stage developer option

The tooltip open delay (Q6) is a per-viewer option, default 330 ms, clamped to 0 to 2000, stored as `hrifa.stage.tipDelay.v1` (`kit/settings.ts`). `StageApp` has a "Developer" popover with the number field and provides the value through `TipDelayContext`; `Tip` reads it with `useTipDelay`.

### Not done / open

Merged in M5: the slot strip is the kit `Strip` and `StripTool` inside a compact `KitScope` (`Slot.tsx`); the Stage's own copy of the strip tokens is gone. Kit rows are one height at xs: input, select and number fields read `--input-height-xs`, `ActionButton` reads `--button-height-xs`, the segmented control and the toggle are set to `--kit-row-height` in `kit.module.css`. A persisted density choice is not built.
