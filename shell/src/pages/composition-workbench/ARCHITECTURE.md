# Composition Workbench Data Contracts

Status: preliminary v0.1  
Date: 2026-08-17

## Purpose

Composition Workbench nodes exchange intelligible musical data. A packet describes three independent things: its structural kind, the domain meaning of its values, and the frame in which those values operate. Provenance records where each item came from and which operation produced it.

The model deliberately avoids creating a nominal data class for every node result. An interference resultant is not a special `RhythmCycle` object. It is a list of durations whose role is inter-onset spacing, framed as a cycle.

## The three axes

### Kind: how the data is structured

The preliminary structural vocabulary is:

| Kind     | Meaning                                              |
| -------- | ---------------------------------------------------- |
| `value`  | One atomic value.                                    |
| `list`   | An ordered collection.                               |
| `tree`   | A hierarchical collection.                           |
| `bank`   | A named or indexed collection of peer alternatives.  |
| `events` | Time-positioned musical events.                      |
| `layers` | Simultaneous or independently aligned streams.       |
| `curve`  | Sampled or functional values over a continuous axis. |

Kinds describe structure only. They do not imply musical meaning.

### Domain: what the values mean

Initial general domains are `integer`, `rational`, `duration`, `onset`, `pitch`, `pitchClass`, `interval`, `note`, `boolean`, `symbol`, and `text`.

The current construction engine also uses explicit operation-level domains: `cycleLength`, `pulseCount`, `phaseOffset`, `parameterFrame`, `rhythmPattern`, and `rejectedFrame`. These remain distinct where confusing them would change an operation's meaning or validity.

### Frame: where the data exists

A frame supplies context that should not be smuggled into the values:

- `topology`: `linear` or `cyclic`
- `unit`: currently `abstract`, `pulse`, `millisecond`, `beat`, or `quarterNote`
- `extent`: the length of the framed region
- `origin`: the frame's reference position
- `grouping`: optional named grouping, unit length, and boundaries

A role can further identify how a domain is being used. Current roles include `interOnset`, `generatorValue`, `pitchMaterial`, `parameter`, `pattern`, and `rejection`.

## Packet contract

```ts
interface DataPacket<T> {
  kind: DataKind;
  domain: DataDomain;
  encoding?: DataEncoding;
  role?: DataRole;
  frame?: PacketFrame;
  items: DataItem<T>[];
  metadata?: Record<string, unknown>;
  warnings: string[];
}
```

Every item has a stable ID, value, and provenance entries. Provenance identifies source node instances and source item IDs, names the transformation, and may record its parameters. Operations should preserve inherited provenance and append their own transformation.

`encoding` records how values express their domain when that distinction matters. It is separate from the temporal unit in a frame. Current pitch encodings are `midi-note`, `midicent`, `note-name`, and `chromatic-12`.

## Interference output

The Interference node emits its resultant as:

```ts
{
  kind: 'list',
  domain: 'duration',
  role: 'interOnset',
  items: [2, 1, 1, 2],
  frame: {
    topology: 'cyclic',
    unit: 'pulse',
    extent: 6,
    origin: 0,
    grouping: { /* selected Schillinger grouping */ }
  }
}
```

The interface shows the packet fields with ordinary, typeable separators: `list | duration | inter-onset | cyclic`. The values answer what occurs between resultant attacks; the frame carries recurrence and grouping. Each duration item points back to the generator or generators responsible for its starting attack.

Every authored generator is also published as a named cyclic inter-onset output. A generator pattern such as `2 1 3` retains those values and a local frame extent of `6`; it is not redundantly expanded to the resultant recurrence. Generator ports use the draft's stable ID while their displayed labels may be renumbered. Melodicization's Rhythm source input lists the resultant and every valid generator lane.

### Mathematical background: what these operations actually are

Binary synchronization (`r_{a÷b}`, Schillinger ch. 2, implemented in `interference.ts`) is not a Schillinger-specific invention: unioning two arithmetic progressions of spacing `a` and `b` inside a window of length `ab` is the classical construction of a **Christoffel word** — equivalently, marking where a straight line of slope `a/b` crosses the horizontal and vertical lines of an integer grid (the same idea behind Bresenham's line-drawing algorithm). For coprime `a, b` the result has exactly two duration values arranged palindromically; that is precisely the **balance property** the Morse–Hedlund theorem uses to characterize Sturmian sequences, and it is the periodic (rational-slope) case of the same cut-and-project construction that generates aperiodic quasicrystal tilings at irrational slopes. Godfried Toussaint's *"The Euclidean Algorithm Generates Traditional Musical Rhythms"* (2005) traces this same territory and cites Schillinger's interference-of-periodicities as a precursor to what he calls Euclidean rhythms (Bjorklund's algorithm — see the separate `euclidean-rhythm` node in Construction). The two constructions are not identical — Euclidean rhythms distribute `k` onsets maximally evenly among `n` slots; Schillinger's resultant unions two independent clocks — but they frequently coincide for coprime pairs and are worth cross-checking against each other rather than treated as unrelated.

Fractioning (ch. 4, `fractioning.ts`) has no equally canonical name in the literature. Its "restart at every block boundary" mechanic is what breaks the self-similarity that makes Christoffel words special, so it is best understood as a Schillinger-specific device rather than an instance of a known object — though it's structurally close to running-bond (staggered) brick tiling, and to interleaving techniques in coding theory/DSP that deliberately stagger a repeating sub-pattern across block boundaries.

Pair composition (ch. 5, `pairComposition.ts`) is a formal/structural device — concatenating and padding statements to a balanced length — closer to classical antecedent-consequent phrase pairing than to a distinct mathematical object.

## Pitch List input and output

Pitch List reads either its inline list or a connected upstream list. A connected input always takes precedence; the inactive inline values are not combined with it.

The `Read list as` control is an explicit interpretation rather than an automatic cast:

- MIDI notes: `60, 62, 66.5` produces `list | pitch | midi-note | pitch-material`.
- Midicents: `6000, 6200, 6650` produces `list | pitch | midicent | pitch-material`.
- Note names with octave: `C4, D4, F#4` produces `list | pitch | note-name | pitch-material`.
- Pitch classes: `0, D, F#` produces `list | pitch-class | chromatic-12 | pitch-material`.

Every outer-list item is normalized to a pitch group. An unbracketed value is a one-pitch group; brackets preserve simultaneous membership, so `60 [60 64 67] 62` contains three groups and five pitches. The group remains intact through provenance and downstream transformations rather than being flattened into unrelated pitch items. Nested or unmatched brackets are rejected explicitly.

MIDI-note decimals and midicents retain microtonal precision. Note-name spelling is retained alongside a normalized midicent value used for playback. Pitch-class integers must be from 0 through 11; the interpreter does not silently apply modulo.

Pitch classes have no register. Their preview octave is a listening control only and does not change the output into concrete pitches. A later register or voicing operation must perform that conversion explicitly.

The Forte set-class catalog is an authored source for inline pitch-class material. It contains all 223 non-empty set classes of cardinalities one through twelve, using the conventional extended Fortean labels outside Forte's original cardinalities three through nine. It exposes Forte number, prime form, interval-class vector, complement, and Z-mate where applicable; `0-0` appears only as complement metadata for `12-1`. Choosing a catalog entry creates one bracketed simultaneous pitch group, never a sequence of unrelated pitch items. Transposition and I0 inversion are explicit selection parameters; neither assigns register.

Catalog insertion adds a `select-forte-set` provenance step to the affected pitch group before `read-as-pitch-class`. Manual editing deliberately clears catalog attribution because the resulting text can no longer be claimed as the catalog selection. Replacing values may change Pitch List to pitch-class interpretation; inserting alongside existing values is available only when the current pitch-class list is valid.

Preview step duration, gate, and volume are realization controls. They do not become part of the pitch-list output. Gate may extend to 200% of the step duration, allowing adjacent preview notes to overlap.

All node volume faders use the shared `VolumeControl` and gain conversion. Preview sources feed that master at nominal unity. The control maps 100% to gain 1 (0 dB), 0% to gain 0 (negative infinity dB), and reports intermediate amplitudes on the logarithmic dB scale. Nodes must not compensate for the shared control with another hidden output level, fader curve, or readout. Any future musical velocity or accent data must remain explicit and separate from the node master.

## Realization and shared audio

Audio is a consumer of musical packets, not a second source of compositional data. Nodes retain ownership of their typed outputs. A pure realization step combines those outputs with explicit listening controls and produces a `PerformancePlan` containing normalized, time-positioned events. The plan retains source provenance and is not persisted.

Performance plans declare one of two non-interchangeable timebases:

- `musical` plans store exact rational positions and durations measured in quarter notes. They carry a tempo map, meter map, and display-tick definition. Tone schedules their onsets on its transport and resolves durations to audio-clock seconds only at the rendering boundary.
- `seconds` plans are reserved for deliberately wall-clock-based auditions, such as the current “300 ms per pitch” preview. Seconds must not be inferred for composed musical events.

Source packets may retain local temporal units such as integer pulses. Turning a pulse into a sixteenth note, beat, or other metric duration is an explicit interpretation. The shared utilities accumulate those mapped durations without floating-point drift.

The interface may present a musical position in Bitwig-style `BAR.BEAT.TICK.%` notation. Bars and beats are resolved through the meter map; the tick is a configurable display subdivision; the percentage supplies sub-tick placement. This notation is a contextual formatter and parser, not the canonical stored value. Changing the display subdivision must not move an event.

The workbench owns one lazily started `AudioEngine`. It centralizes browser audio activation, Tone.js scheduling, the master output, an instrument registry, and named buses. Each playback request returns a source-scoped session with live bus gain and independent stop behavior. Starting another preview from the same source replaces that source's prior session without stopping other nodes.

**Looping.** `PlaybackRequest.loop` repeats a musical plan seamlessly until stopped, using Tone's transport loop points over one pass (the plan's own `duration`, not the click-extended length `applyTransport` produces). A count-in sounds once, before the loop begins; the meter click restarts each pass. Loop points are whole ticks, so a pass that is not a whole number of ticks (a 7-tuplet at 960 PPQ) is rounded, drifting under half a tick per pass. `onComplete` never fires for a looping session, `clock()` reports `loopSeconds` for a wrapping playhead, and stopping releases the global loop. Seconds plans cannot loop. The mixer sets `loop` from its `loopable` result.

Standalone rhythm and pitch nodes may create provisional seconds-based audition plans. Their local gate, register, and instrument choices remain realization controls and do not alter their output packets.

**Global transport.** Tempo, meter, pulse value, metronome, and count-in are workbench-wide settings (`transport.ts`, stored in `compositionSettings.tsx`, edited in the header `TransportBar`). Every rhythm preview takes its pulse length from the transport (`pulseSeconds`) instead of a per-node unit, and passes `followTransport: true` so the engine adds meter clicks (on the `meter` bus, whose gain is the metronome switch, so it toggles live) and an optional one-bar count-in. Melodicization's tempo, display meter, and pulse value are the transport's, so its note output follows the global pulse value. Interference's grouping click is a separate `grouping` bus layered on the meter click. Pitch List keeps its own step length, since a pitch list has no rhythm. **Preview voices.** `sounds.ts` defines two global voice sets (rhythm and metronome), each a base pitch plus primary/secondary/tertiary voices with a sound type (click, pluck, woodblock, drum, tone) and a cents offset. The pluck is a short triangle synth voice with no sustain, between a click and a held tone, sounding at the written pitch. Nodes play layer *n* on voice *n* (`layerSound`) unless the node stores its own `SoundOverride` for that layer (`SoundOverrideControl`): Interference per generator, Rhythm Householder for input (A) and candidate (B, plus an A/B button that plays both), Fractioning and Pair Composition for their single rhythm. Meter clicks use the metronome's primary (downbeat) and secondary voices; Interference's grouping click uses its tertiary. Percussive types sound in a fixed register relative to the written pitch (`soundRegisterSemitones`). Nodes register their main preview with `useTransportPreview` so the header Play button and the space bar start the selected node; Stop and space-while-playing stop every preview. A composed rhythm-and-pitch result should instead pass through an explicit combination operation that emits `events | note` in musical time; playback must not pair unrelated packet streams invisibly.

Tone.js is contained behind the Hrifa-owned engine contract. Node components and musical operations do not import Tone classes, which keeps the realization compiler testable and leaves room for later renderers such as offline export or Web MIDI.

## Browser persistence

The workbench treats authored state as durable browser state. The active view and node, node inputs, interpretation and combination settings, preview controls, piano-roll viewport and inspector preferences, and live input bindings are versioned in local storage and restored on refresh. The desk is the exception: it lives in IndexedDB (see History, storage and projects), and per-viewer editor preferences (`hrifa.note-editor.v1`, `hrifa.data-block-defaults.v1`, `hrifa.developer-options.v1`) sit outside the workbench key prefix, so saved projects never capture them. Derived packets and audio sessions are rebuilt rather than serialized.

The project pitch set (the "key" chord input offers chords from) is a composition setting (`compositionSettings.tsx`, field `pitchSet`), so it persists under the settings key and travels with saved projects. It stores `{ edo, pcs, preset, tonic }`: `pcs` is authoritative (toggled pitches persist), `preset` and `tonic` are the last shortcut used. Default: major on C at 12-EDO, chromatic at any other EDO. Loading validates it (integer pcs in 0..edo-1, known preset, tonic in range, `edo` equal to the settings EDO) and falls back to the default for the settings EDO otherwise, so an older blob without the field loads with the default and the storage key is not bumped. Changing the EDO therefore resets the set to the new EDO's default. The settings panel edits it (preset and tonic pickers, one toggle chip per pitch class). `projectPitchSetFromPreset` outside 12-EDO stores chromatic and tonic 0 when any other preset is asked for (a request for `chromatic` itself keeps the given tonic; the tonic picker is disabled outside 12-EDO), because the presets are 12-EDO step patterns (`chordInput/pitchSet.ts`) and no diatonic pattern is defined elsewhere (W-13, W-14). The set is the "key" the Chords tool reads (see Chord input below); the picker never writes it.

A node's Reset control is the explicit request to replace its durable state with that node's defaults. Resetting a node affects only that node's state; it does not silently erase independently authored state of other nodes.

**Stored names after the node rename (W-55).** The canvas processor is a node and the canvas graph is the node tree. Stored: the placed-instance records use `nodeId` (was `moduleId`); localStorage keys `hrifa.composition-workbench.routing.node-routes.v1` (route states per instance) and `hrifa.composition-workbench.ui.active-composition-node.v1` (the active node); the inspector and selection targets use `kind: 'node'` and `level: 'node'`; the dock panel id is `node-detail`; the React Flow node type is `node`; the DOM marker is `data-node-slot`; the desk record field `origin.nodeInstance` (was `origin.moduleInstance`, IndexedDB) and the packet metadata `sourceNodeInstance` (was `sourceModuleInstance`). Code: `nodeRegistry.tsx`, `nodeEvaluators.ts`, `nodePorts.ts`, `nodeState.ts` and `nodeState/`, `useNodeEvaluation`, `useNodePreview`, `NodeHost.tsx`, `NodeDevice.tsx`, `NodeShell.tsx` (the shared card shell, was `Module.tsx`), `NodeEvaluationRunner`, `NodeInstanceHost`, and the 13 `*Node.tsx` components (`DataBlockSourceNode` is Make source). The CSS module files keep their names (`Module.module.css`, `ModuleDevice.module.css`, `ModuleHost.module.css`). Old browser data under the old keys is simply not read (baseline reset, no migration).

## Chord input

The Notes editor's Chords tool (tool key `7`) enters harmony without placing notes one at a time: a click on a pitch, or on an existing note, anchors a chord picker, which previews chords as ghosts in the roll and places them as ordinary notes. Everything musical is pure TypeScript under `chordInput/` (no React, no audio); the editor and the picker only wire it. Files: `pitchSet.ts` (the key), `chordTemplates.ts` (vocabulary), `chords.ts` (which chords a set offers), `voicing.ts` (chord to midicents), `placement.ts` (chord and clicked cell to notes), `navigation.ts` (keyboard stepping as data), `ChordPicker.tsx` (body), `ChordPickerPanel.tsx` (the body bound to the session), `ChordsPanel.tsx` (the `chords` panel's frame), `ChordPanelBridge.tsx` (session to Stage), `chordReady.ts` and `useChordReady.ts` (the panel's ready line value), `placeChords.ts` (the stack rule and the merge of several anchors). Decisions: W-13 to W-22, W-25 (superseded by W-48 for placement).

**Pitch set** (`pitchSet.ts`, W-13). `PitchSet { edo, pcs }`: `pcs` are absolute pitch classes, integers in 0..edo-1 in exact EDO steps, sorted and unique (pc 0 is C at 12-EDO, as in `pitch.ts` `pitchClassName`), not relative to a tonic. `PITCH_SET_PRESETS` (major, natural/harmonic/melodic minor, the other modes, major and minor pentatonic, chromatic) are 12-EDO step patterns that fill the set from a tonic (`presetPitchSet(preset, tonic, edo)`); for any other EDO every preset returns the chromatic set. After a preset the set is just pitches: `togglePitch`, `addPitch`, `removePitch`, `makePitchSet` edit it, so C major plus F# is valid and both D-F and D-F# chords appear. The project's set is `CompositionSettings.pitchSet` (see Browser persistence): default major on C at 12-EDO, chromatic elsewhere, and a change of project EDO does NOT map the old pitches (no scaling, toggles are lost): `updateSettings` runs `sanitizeCompositionSettings` on every update, so the set whose `edo` no longer matches is replaced at once by the new EDO's default, and loading does the same for a stored blob (W-14). The picker can override the set for itself only: `chordOverride` (a `ProjectPitchSet`, honoured only while its `edo` equals the settings EDO) and, in common-tone mode, `allPitches` (offer chords over the chromatic set); both are editor tool state, never written to settings, reset on reload. The picker never edits the project set.

**Chord templates** (`chordTemplates.ts`). A `ChordTemplate` is `{ id, suffix, steps, roles, tier }`: `steps` are the interval stack in EDO steps from the root (ascending, first 0, may exceed the EDO: a 9th at 12-EDO is 14, so voicing keeps stacking order), `roles` one `ChordRole` per tone, pitch class = (root + step) mod edo. `CHORD_LIBRARY_12` is the named 12-EDO library, frozen, simple templates first: 20 simple (triads, 5, sus2, sus4, 6, m6, sevenths, 9, m9, maj9, add9, madd9) and 21 extended, the vocabulary of the human's sheet (altered fifths and ninths, 6/9, 13, maj11, add#11, 7b9#11, m7b11, ...). Names are root plus `suffix` at 12-EDO (`Am7`). For any other EDO there is no named library: `degreeStackChords(set, rootPc)` stacks scale degrees of the set at offsets 0, 2, 4 (triad), 6 (seventh) and 8 (the 2nd an octave up), emitting a stack only when no degree repeats modulo the set size, as `simple` templates with roles root, 3rd, 5th, 7th, 2nd; names are the spelled root and the step stack in brackets (`D[0-6-11]`, bare number where the EDO has no letter spelling). Proper naming outside 12-EDO is deferred (BACKLOG). There are no automatic chord groups: a chord is only a recipe for notes; once placed the notes are independent.

**Chord engine** (`chords.ts`). One function, `findChords(set, { root?, contains? }, { tier? })`, returns every `Chord` (`name`, `templateId`, `edo`, `rootPc`, `steps`, `roles`, `tier`, `pcs`) whose tones ALL lie in the set; a chord with a tone outside the set is not offered. Output is simple chords first, then extended (only when `tier: 'extended'`), each keeping root and library order. `chordsOnRoot(set, rootPc, options)` is root mode (`{ root }`); `chordsWithCommonTone(set, pc, options)` is common-tone mode (`{ contains }`), grouped into `ChordColumn`s by the role the pitch plays in each chord (`roles[pcs.indexOf(pc)]`), columns in `ROLE_ORDER`, empty ones omitted. `chordName` is the single place names are made. The picker is the only caller in the editor.

**Voicing engine** (`voicing.ts`). `voiceChord(chord, anchor, { inversion, spread })` and `voiceChordTones` (the same, keeping each voice's chord-tone index) turn a chord into ascending midicents, all arithmetic in integer EDO steps (pitch = anchor + step difference x 1200/edo, unrounded, so non-12 EDOs stay exact). Order: (1) inversion `k`: with `n` tones, tone `k mod n` becomes the bass and every lower-indexed tone is raised by whole octaves above it, which is the close voicing of that inversion (an inversion of `n` or more wraps by octaves, which an anchor cancels); (2) spread, applied to the close voicing: `close` unchanged; `drop2` lowers the second voice from the top one octave (needs 3 or more voices, otherwise unchanged); `drop3` lowers the third from the top (4 or more); `open` raises the voices at odd positions from the bottom (V1, V3, ...) one octave (2 or more voices, so on a dyad the upper voice rises an octave, on a triad the middle, on a seventh the 2nd and 4th); (3) anchor: `{ kind: 'bass', midicents }` pins the LOWEST sounding voice and ignores pitch class (after a drop the dropped voice is the lowest and is the one pinned), `{ kind: 'tone', index, midicents }` pins chord tone `index` exactly at `midicents` whatever the inversion or spread. Placement uses `tone`, never `bass`. `voicingFor` holds a global inversion at a chord's last one (a triad has 2, a seventh 3), so one choice works across chord sizes. Invalid input throws `RangeError`: an EDO that is not a positive integer, steps not strictly ascending, an unknown spread, an inversion that is not a non-negative integer, a `tone` anchor index not in the chord; `chordToneIndex` also throws for a pitch class the chord lacks. The function is pure so a later voicing-exploration feature can reuse it.

**Placement, audition, ghosts and pinning** (`placement.ts`, `NotesEditor.tsx`). Register rule (human decision, M4): the clicked pitch is the chord's ROOT tone and stays exactly at the click; inversion and spread put the other voices around it, inverted tones below (Am first inversion at A4 is C4 E4 A4; C major first inversion at C4 is E3 G3 C4). In common-tone mode the anchored tone is the chord tone whose pitch class was clicked (`chordToneIndex`), so the clicked pitch sounds where it was clicked; a pitch class not in the chord falls back to the root. `voiceAtAnchor` snaps the click to the EDO grid (`snapToEdo`) and drops voices outside 0..12700; `chordNotes` makes one `PlacedNote { pitchMidicents, start, duration }` per voice at the anchor's onset. Placement goes through the existing edit contract: the editor builds the notes with `chordNotes`, gives each a new item id (`newNoteItemId`), and commits ONE `addNotes` (`notesEdits.ts`) through the editor's `commit`, so each insert is a single history entry and a single undo step, the new notes become the selection, and the result is ordinary single-pitch note items with one shared onset (one chord slot for `noteTransforms`, recoverable by the selection and same-onset tracing; nothing links them). `addNotes` skips a note whose start and pitch already exist; an insert that adds nothing writes nothing. The entry velocity is the editor's, the length the last-used entry length, else one grid step (a note anchor uses the note's own, see Stacking). Ghosts are the same function as insert (`voiceAtAnchor`), so a ghost shows exactly the notes that would be placed: a hover ghost for the chord under the pointer in the picker (silent), a pinned ghost for the chosen chord (a click or arrow selection pins it and the hover ghost is not drawn for the same chord), an anchor ghost on the clicked cell (labelled by `pitchLabel`; `chordAnchorLabel` developer option puts the label on the note or beside it) and a one-step hover-cell ghost under the pointer; the roll draws them through `ghostNotes`. Audition (`ChordAudition`, mounted only while the tool is active): a single click on a chord, an inversion button or a spread button pins it and sounds it through the desk's preview path: an ad hoc one-item note packet (all pitches in one item, velocity 0.8, at least a quarter note long, never added to the data-block) goes through `createNotePacketPerformancePlan` and `useNodePreview` under source id `chords:<data-block id>`, with the transport's timeline. The `chordPreviewGate` developer option (`hrifa.developer-options.v1`) decides whether a plain click sounds (`click`, default) or only Ctrl/Cmd+click (`ctrl-click`); hover never sounds, and a double-click or Enter inserts (the second click of a double-click does not audition again). Key presses count as clicks for the gate.

**The Chords panel and viewer preferences** (M6a; supersedes W-16 and W-25). The picker body (`ChordPicker.tsx`) takes the anchor, the project set, the override, mode, tier, voicing and callbacks (`onHover`, `onPin`, `onInsert`, `onClose`, ...) as props, lays itself out from its container, and knows nothing of its host or the roll. `ChordPickerPanel` binds it to the chord session, and `ChordsPanel` frames it as the page's `chords` panel (tab "Chords", home `Tools`, registered in `layout/workbenchPanels.tsx`, rendered by the Stage once through a portal so moving the tab between dockers or flipping workspaces never remounts it; the frame carries `data-chord-scope`, so the W-20 keys and Esc work with focus in it). It is an ordinary panel (design 3.6, O3(b)): openness is saved with the workspace like any other panel. **Opening:** `ChordPanelBridge` (mounted by the page inside `WorkbenchSessions`, beside the Stage) calls the Stage's `show('chords')` when the active claim starts wanting the picker (the Chords tool is on), when the claim's target changes and when the active workspace changes, so the panel opens in its remembered docker (`lastDocker.chords`, design 3.3) and comes to the front. The bridge is the only caller of the Stage for `chords`. **Leaving the Chords tool does not close the panel** (decision 1b); the panel then acts on the roll's selection (selection mode, below) and says so in its ready line. **Closing:** when the person closes the tab (its x, menu Close, Remove docker) while the claim wants the picker, the bridge calls `session.reportPickerClosed()`, which forwards to the active claim's host (`onPickerClosed`: the Notes editor goes back to `toolBeforeChords`); closing under another tool just closes; a change of workspace is not a close. **No target:** with no claim (opened from the Panels menu with no data-block open) the ready line says "No target: open a data-block to insert" and the panel shows an audition-only picker (middle C, the project's scale, the panel mounts its own `ChordAudition`; insert does nothing), so audition never needs a target. **Hidden roll:** the Notes editor's `ChordTarget.visible()` is false while its root is inside an `inert` (parked) host, so the W-20 keys are not captured while another tab is in front of the Notes editor, and clicking back restores them (design 8.4). The Notes editor no longer contains the picker, its own Stage or the canvas takeover; the roll fills the Notes editor panel. Per-viewer preferences live in `hrifa.note-editor.v1` (`noteEditorPreferences.ts`). The mode (Root | Common tone), tier, override, voicing and continuous insert are editor tool state in the chord session. Tests that render the editor without a Stage use `chordInput/chordTestUtils.tsx`, which shows the panel while a claim wants it (`always`: whatever the tool, for selection mode).

**Selection mode** (M6b, design 7.7, SCENARIOS.M6.md B1 to B6, decisions 3a and (i)). While the claim's tool is not Chords (`isSelectionMode()`: a target and `pickerWanted` false) the panel stays open (1b) and acts on the roll's current note selection, through the chord target only; the roll knows nothing of the panel. `ChordTarget` gained two optional members: `selectedNotes(): ChordNoteHit[] | null` (the host's selected notes, `null` nothing selected, `[]` a time range with no notes; the Notes editor derives it from `selectionRef`, the same pruned, derived selection `publishNoteEditor` and `shownSelection` use, and calls `claim.changed()` when the selection or the notes change) and `insertMany(requests)` (several anchors in ONE host commit, one undo step; REQUIRED for a host that has `selectedNotes`: without it the session places nothing and the ready line says "This host cannot insert several chords", it never falls back to one undo step per chord). `ChordTarget` also has `label` (a display name for a host that is not a roll) and `meter` (for "bar X beat Y"). Each selected note becomes an anchor by the same rule as a click on it with the Chords tool (`anchorOnNote`: the note's exact pitch snapped to the grid, its onset, length and velocity, W-22), so one selected note gives exactly what the Chords tool, a click on that note and Enter give. **Anchor order:** the anchors are sorted by onset, then pitch (never the data-block's data order), so the picker lists chords from the earliest, then lowest, selected note (middle C when none) and the merge below always gives the same result. **Root mode with several notes** puts the same chord type on each note (the chord's quality on each note's pitch); common-tone mode puts the same pitch classes around each note. `chordInput/placeChords.ts` merges the requests: the stack rule per request (W-22: a tone overlapping an existing note of the same pitch is dropped, so an existing note is never duplicated) and, across requests (C2), a tone is dropped only when an earlier request's tone has the same pitch AND the same onset (the earlier anchor's length and velocity win); the same pitch at different onsets that merely overlap in time is kept at both. In selection mode the picker hides Continuous and the anchor key hints (no anchor to move). Audition always works in every state. **Insert gestures in selection mode:** double-click a chord, Enter on a focused chord button, and Enter with focus elsewhere in the panel (the session's key handler, in scope only inside `[data-chord-picker]` or `[data-chord-scope]`); Enter in the roll, Esc and the other roll keys keep their own meaning (selection mode never captures keys outside the panel, and Shift+arrow anchor moves and `i` (continuous) are anchor-mode only). **After an insert (B2) the selection stays on the notes the person had selected (the anchors), not the inserted notes**, so a second double-click stacks again on the same notes; a Chords-tool (anchor mode) insert still selects the inserted notes. **Selection ghosts (M6c):** the roll draws ghost notes for the chord the picker would insert on EVERY selected note. `useSelectionGhosts` (`chordInput/useChordGhosts.ts`; the editor passes `chordGhosts ?? selectionGhosts` to the roll's `ghostNotes`) builds the requests with `session.selectionRequests(chord, target)` (the same list `insertOnSelection` hands the host) and runs `mergeChordInserts` against the data-block's notes without committing, so a tone the stack rule or the same-onset merge drops is not ghosted and the ghosts equal what Insert adds. Triggers are the anchor-mode picker events: the hovered or keyboard-focused chord (`hoverChord`, variant `hover`) and the pinned chord (a click, variant `pinned`; a hover of the pinned chord is not drawn twice), with the existing ghost styling and no anchor ghost. They clear when the selection empties, the chord is un-hovered or un-pinned, the tool or claim changes (the hook is off unless this editor's claim is in selection mode), and after Insert (`clearGhosts`). **A new selection resets the pin (M6c):** the session remembers the selected notes (`pitch@onset`, from `selectionAnchors()`) each time the host calls `claim.changed()`; when that set differs from the last one seen in selection mode, `pinnedChord` is cleared (hover is kept), so the new selection shows ghosts only for a hovered or newly clicked chord. An Insert keeps the anchors and an undo restores the same notes, so neither counts; anchor mode keeps its own pin rules. **Selection mode needs the panel on screen:** `ChordSessionState.panelShown` (default true for a host with no Stage) is set by `ChordPanelBridge` after every commit from the Stage's `isShown('chords')` (open, front tab, docker expanded); read in an effect because the Stage's answer is one render behind during render. While it is false (panel closed, behind another tab, docker collapsed or in another workspace), `isSelectionMode()` is false, `isIdle()` makes `insertChord` and `handleKey` do nothing, the provider's key listeners are off, `useSelectionGhosts` returns nothing, and hiding the panel clears hover and pin. The panel's ready line is inside the panel, so it cannot claim an Insert while hidden. Anchor mode (Chords tool) is unaffected: it opens the panel itself.

**Chord roles, tiers and the sheet reference** (M6b; `chordInput/chordTemplates.ts`, `chords.ts`, `ChordPicker.tsx`). A chord tone's role is its scale degree: `root | 2nd | 3rd | 4th | 5th | 6th | 7th`. A ninth tone (b9, 9, #9) is the `2nd`, an eleventh the `4th`, a thirteenth the `6th`, and altered fifths (b5, #5) stay `5th`, so Am9 is root, 3rd, 5th, 7th, 2nd; the chord name says whether it is an extension. The common-tone column headers show the degree (`2nd`) and a tooltip names the extension (9th, 11th, 13th). Every template has a `ChordTier`: `simple` (triads, 5, 6, sevenths, add9, plain 9ths) or `extended` (altered fifths and ninths, 6/9, 13, 11ths, add#11 and the rest of the human's sheet, 21 templates). `findChords`, `chordsOnRoot` and `chordsWithCommonTone` take `{ tier }` (default `simple`; `extended` returns simple first, then extended, each in library order; non-12-EDO degree-stack chords are simple). The picker's Simple | Extended buttons next to Root | Common tone set the tier, which is editor tool state (`NotesEditor`, default simple, kept across clicks and tool switches, reset on reload, never written to settings) passed to `ChordPicker` as `tier` and `onTierChange`; the picker is the only caller of the engine in the editor, so lists, keyboard navigation, the fallback chord, inversion counts, ghosts, audition and insert all see the same tier. A tier change clears the pinned and hover ghosts (the chord may have vanished; the current chord falls back to the first listed). The human's original sheet is kept at `arcs/workbench/reference/any-chord-voice-relations.csv` and `chordInput/sheetParity.test.ts` checks the templates against it, so a new template or a role change must agree with the sheet or be listed there as a documented exception.

**Chord input shortcuts, sticky mode and continuous insert** (Chords tool, `NotesEditor.tsx`, `chordInput/ChordPicker.tsx`, `chordInput/navigation.ts`). The mode is sticky: only the Root | Common tone buttons set the stored `chordMode`; a plain click on the roll opens it, and Ctrl/Cmd+click opens common-tone mode for that click only (`chordCtrlOpen`, cleared by the next click or a mode button), so the buttons show the effective mode of the open picker while the stored one is untouched. While the tool is active and an anchor exists, ONE capture-phase `keydown` listener on the window, scoped to this editor (its own root element, the picker in the dock or the takeover, or the page body; never a target with its own arrow keys: `separator`, `slider`, `tablist`, `menu`, `menuitem` roles and Accordion controls, so the Stage's column splitters and the velocity lane splitter keep their keyboard resize), runs the key map, ahead of the roll's own arrow handling (which would edit the selection) and consuming (`preventDefault` + `stopPropagation`) only the keys it handles: arrows browse the chord array (the picker's navigation, exposed to the editor as `ChordPickerControl` through `controlRef`, so the picker's own arrows and the editor's keys share `stepChordKey`; moves DOM focus only when focus is already in the picker, and pins the chord's ghost), Enter inserts (the pinned, else hovered, else current chord; Enter on any button is the button's own), Alt+Down/Up inversion next/previous (Alt+Down steps root -> 1st -> 2nd, Alt+Up back) and Alt+Left/Right spread previous/next, both CYCLING (after Drop 3 comes Close and back; the inversion wraps within the current chord's own tone count, so every press moves the ghost; through the same `changeVoicing` as the buttons; a handled key is always consumed, even when nothing changes), Shift+arrows move the anchor (Left/Right by the anchor's grid step, not before 0; Up/Down by exactly one EDO step, 1200/edo cents (100 at 12-EDO), from the grid-snapped anchor, clamped to 0..12700; the picker re-lists for the new pitch and the current chord is re-pinned, else the first), `I` toggles continuous insert, Esc closes. Auto-repeat: Enter and `I` ignore repeats (no repeated inserts or toggle flicker), repeated arrows still navigate but never sound; the Alt keyup after a handled Alt+arrow is swallowed in the same effect, wherever focus is, and resets the flag. Ignored in INPUT/TEXTAREA/SELECT/contentEditable, comboboxes and listboxes, while a dialog or menu is open, and with Ctrl/Cmd held. Key presses count as clicks for the preview gate (sound only in `click` mode). Continuous insert is tool state (off by default, reset on reload): after an insert the anchor moves along time by the chord length (same pitch), the chord and voicing stay pinned and the ghosts follow, so the next Enter places the next chord; each insert stays one `addNotes` commit, one undo step. The view follows the anchor: `setChordAnchorTo` (every key anchor move and every continuous advance) bumps the roll's `reveal` token with the span variant `{ start, end, pitchMidicents, pitchEndMidicents, token }` (the anchor's chord, plus the next chord when continuous insert is on, and 600 midicents of pitch room each way for the ghost), so the roll scrolls the minimum amount, and not at all when the span is visible. The picker marks the current chord (`data-current`, `aria-current`, the accent tint of a pressed option) from its current key, whatever has DOM focus, in the root grid and the common-tone columns, and scrolls it into view (nearest edge, clear of the sticky role header) when it changes; a clicked or key-navigated (pinned) chord is the current chord. A keyboard anchor move (Shift+arrows, continuous advance) hides the pointer's hover-cell ghost (`hoverBlocked`) until the pointer reports another cell or leaves. A click on the roll sends no reveal (the point is already in view). An insert that adds nothing (every note already there) writes nothing and no undo step.

**Stacking on an existing note** (M7; `NotesEditor.tsx` `noteAtCell`, `ChordPicker` `onNote`). With the Chords tool, a click (plain or Ctrl/Cmd) on an existing note anchors there: the editor resolves the note from its own notes (no `PianoRoll` change): among notes within 50 midicents of the clicked row whose span overlaps the clicked cell, the one whose start is nearest the cell (the smaller start on a tie, whatever the packet order). The anchor takes the note's exact pitch (snapped to the EDO grid) and its actual onset (not the cell start), and carries `note: { duration, velocity, pitchMidicents }` (the note's real pitch): the stack's length is the note's duration (the last-used entry length only applies to empty-cell clicks) and the new notes take its velocity. The picker header reads `On C4 (note): chords on C`, with the cents offset when the note's real pitch differs from the snapped anchor by more than 1 midicent (`On C4 +30c (note)`). The pointer-hover ghost is suppressed over the note anchor's span and pitch row. Insert never modifies any existing note: it drops every tone that would overlap ANY existing note of the same pitch (same onset, an earlier longer note still sounding, a later note inside the stack span; pitch tolerance min(50, stepCents/2) midicents with stepCents = 1200/edo, so an off-grid C4 +30c counts as the C and adjacent steps of a fine EDO are not merged), so nothing is moved, split, trimmed or deleted and the W-9 resolution has nothing to do (empty-cell chord placement is unchanged and keeps W-9 'the new note wins'); the rest go in as ONE `addNotes` commit (one undo step, nothing written, picker stays open, when every tone is dropped). Stacked notes are ordinary same-onset single-pitch notes, i.e. one chord slot for `noteTransforms`. Shift+arrow moves and continuous-insert advances drop the `note` context (ordinary empty-cell anchors). An empty-cell click is unchanged.

**The data-block editor session, input scope and selection chain** (M4b; `dataBlockEditorSession.ts`, `DataBlockEditorSessionProvider.tsx`, `inputScope.ts`, `InputScopeProvider.tsx`, `selectionChain.ts`, `WorkbenchSelection.tsx`, all mounted by `WorkbenchSessions`, which the page mounts since M4c: see below). `DataBlockEditorSession` is a store of named slots (`DATA_BLOCK_SLOT`: view, tool, toolBeforeChords, ramp, pick, rotation, selection with basis and moves, reveal, announcement) with ONE state object per data-block id: it is created lazily on first read (reads are pure and never dispose or notify), editors attach per data-block from an effect (`useDataBlockAttachment`, refcounted), and a data-block's state (its slots and `onDispose(dataBlockId, run)` disposers) is dropped only in the attach cleanup when that data-block's count reaches 0. So switching A to B gives B fresh state, a closed and reopened data-block starts fresh, two editors on different data-blocks under one session never touch each other, and there is no React key above the Stage. An editor that remounts the same data-block in one commit reads the old state for its first render only; the old editor's cleanup drops it before the new attach, and the notify re-renders the new editor with fresh slots. `openDataBlockId` is the most recently attached data-block that still has an editor. `useDataBlockSlot` is `useState` over a slot (stable setter, functional updates); `NotesEditor` uses it for those values, still keyed by data-block inside its own panel, with a private session when none is above (like the chord session). Nothing here is in the history.

**Mounted by the page** (M4c; `CompositionWorkbench.page.tsx`). The page wraps `AppShell` (the header, the Stage with every panel, the inspector and its data-block actions panel, the status bar) in `<WorkbenchSessions inspectorTarget={shownInspectorTarget} dataBlockId={editorTarget}>`, inside the composition settings, desk and audio engine providers and with no React key, so the canvas, desk and node hosts never remount. `shownInspectorTarget` is memoized (it is the canvas target while a data-block is open) so the provider's selection value only changes with the target. **The page-level chord session** (M4a, W-39; `chordInput/chordSession.ts`, `ChordSessionProvider.tsx`, `ChordPickerPanel.tsx`, `chordGhosts.ts`, `useChordGhosts.ts`, `ChordAudition.tsx`, `WorkbenchSessions.tsx`). ## Ready line

The expected standard for any workbench panel or node that has a main action and waits for a mode, a selection or an input (decided with the human at M6, 2026-11-18, W-49; design record `arcs/workbench/READY-LINE.md`; where this section and that file disagree, this section wins). The first user is the Chords panel (`chordInput/chordReady.ts`, `components/ReadyLine.tsx`); converting the nodes' "Connect ..." placeholders is BACKLOG.

- **What it is.** One line saying whether the panel's main action can happen now and, if so, what it will do. It reports and never acts: not a tooltip, not a toast, not an error.
- **Where.** Directly under the panel's or node's header, above its controls, in the same place in every panel. Always present while the panel has a main action: it never appears or disappears, so the layout never shifts (lab `UI-CONVENTIONS.md` section 1). Fixed height; a long text is cut with an ellipsis and the full text is its tooltip. Panels with no single main action (the desk, the canvas) have no ready line.
- **Three states.** `ready`: what the action will do, with counts ("Insert: one chord on each of 2 selected notes", "Anchor: click in the roll"). `waiting`: the one thing needed next, as an instruction ("Select a note, or use the Chords tool"). `no-target`: why nothing can happen here now ("No target: open a data-block to insert"). Ready is plain text. Waiting and No target are muted (`--text-muted`) and carry an icon, a **different icon for each** (Waiting: fixable here; No target: go somewhere else first), so the state is never shown by color alone. The wording starts with the mode or action name the user can find on screen, in bold (the text before the first colon).
- **One value, two readers.** Each user writes ONE pure function returning `{ state, text }` (`ReadyValue`, `components/readyState.ts`). The line and the blocked action's reason (a tooltip, `aria-disabled` or the disabled control) both read that value, so they never disagree. Things that never need a target (audition, preview) are not blocked by Waiting or No target.
- **Screen readers.** The line's text sits in a polite live region that is updated only when the STATE changes, never on a count or text change inside one state.
- **Scope.** Lives in the workbench (`components/ReadyLine.tsx`, `ReadyLine.module.css`); the icons are inline SVG (no icon package is a dependency). Moving it to `src/components/` (a lock and a DECISIONS row) waits for a second page that needs it.
- **Chords panel texts.** Anchor mode (the Chords tool): "Anchor: click in the roll", with an anchor set "Anchor: Insert places the chord at C4, bar 1 beat 1" (the editor's own "bar X beat Y" in the data-block's meter, `positionWording.ts`, shared with the note's spoken description). Selection mode: "Insert: one chord on the selected note" (n = 1), "Insert: one chord on each of n selected notes", waiting "Select a note, or use the Chords tool" (nothing selected) or "Select a note" (a time range only). No claim: "No target: open a data-block to insert". A host that is not a roll (a list) gets "Insert into <label>" (its `ChordTarget.label`; just "Insert" without one, never the raw id) once it has a position and "Choose where the chord goes" before, and shows no roll wording (no "Chords tool", no "note") in selection mode. The panel header has a fixed height, so the ready line below never moves when Close appears.

## Compatibility and signal routing

Compatibility is checked against all required axes rather than against a node-specific class name. A receiving operation can constrain kind, domain, role, and topology.

The interface groups compatible next operations by intent:

1. **Direct operations** preserve the basic meaning while slicing, rotating, repeating, scaling, or regrouping it.
2. **Musical combinations** combine it with other material, such as assigning pitches or stacking layers.
3. **Interpretations** perform an explicit semantic or structural conversion, such as accumulating durations into onsets or building a rhythm tree.

Composition routing follows a DAW-style pull model. Source nodes expose stable, named output ports but do not place routing actions beside individual rows or outputs. The receiving node owns its input connections, and its I/O section is the single place where the user selects or changes a source. For example, Melodicization's Rhythm source selector may offer `Interference · Resultant` and `Interference · Generator 1`, while Interference itself contains no per-lane `Use in…` buttons.

A receiving input picks its source from a tiered menu (`SourceMenu`), like a DAW's track-then-channel picker: nodes first, each opening to its outputs on hover, click or ArrowRight, with bank entries one level further. A node with one compatible output is a single item ("Pitch List · Pitches"), and a source that has gone missing stays visible in the field but is never offered. The menu's dropdown must not scroll or data-block, or the submenu is shifted back over the parent panel. `compositionOutputOptions` supplies each option's `path` for the tree.

Output port identity uses stable source IDs rather than display indices, so reordering rows does not redirect a connection. Removing a connected output leaves the receiving input visibly disconnected and never silently substitutes another source. Composition-node `Use in…` shortcuts have been removed; routing is selected only at receiving inputs.

Composition view projects those explicit bindings onto a free node tree canvas (React Flow). Position is pure presentation: port and packet contracts remain authoritative about the material flowing through each connection. The canvas header's Add node menu is the single place to create any number of any registered composition node. Every placement is an independent instance with a stable ID, an `x`/`y` canvas position, authored state, named outputs, receiver bindings, and route treatments. Its Inspector removes that specific instance; dragging moves it. Generated sinks follow their producing instance. A new node takes the first free slot, never landing on another. Removing a source leaves receiver bindings visibly missing; removing a receiver removes only the routes it owns. Moving a node never silently rewires the node tree: connections remain explicit objects independent of their spatial presentation.

Tidy (`compositionLayout.ts`, pure and unit-tested) rearranges positions only. It layers nodes by dependency depth so signal reads top to bottom, orders each layer by the average position of its sources to limit crossings, and centres the layers. Cycles are ignored for layering rather than looping.

A route is a first-class non-destructive context between one source output and one destination input. Its context-aware Quick Adjust treatment can perform lightweight operations such as transpose, invert, retrograde, rotate, duration scaling, register assignment, and voicing without mutating the source or requiring a visible chain of primitive nodes. The bottom-left Inspector edits the selected route and exposes bypass and reset. Each active operation appends named provenance to the derived packet in execution order. A treatment should be promoted to a visible node only when it must be named, reused, branched, generated dynamically, or compared independently.

Quick Adjust is generalized across a `signalTypes.ts` registry keyed by the connected packet's signal type (`pitch`, `rhythm`, or the `numeric` fallback for anything else), not by the receiving node or port name. Each entry owns its treatment shape, default, identity check, summary, and pure `apply` function; the Inspector looks up the binding's `signalType` and renders that type's editor generically, rather than each node hardcoding its own route-editing UI. A binding's `signalType` is derived from its connected source (`signalTypeFor`) and resets to that type's default treatment when rewired to a source of a different signal type. This is what lets Arithmetic's A/B inlets — which accept any numeric-ish domain rather than one fixed domain like Melodicization's rhythm/pitch — share the exact same route-binding and Quick Adjust machinery without inventing a parallel system.

The canvas gives routes less visual weight than nodes. An identity route is a bare but generously clickable bezier cable; only an active treatment receives a compact summary badge on the cable. Each cable leaves its source's outlet and enters the receiver's inlet at the exact port tip, and every receiver of an output gets its own cable (there is no shared trunk or junction). The source node reports its downstream-use count on its outlet. Selecting a cable highlights and inspects that receiver-owned route; selecting a node emphasises every cable in its upstream and downstream flow. Equal-looking edge treatments remain independent unless the user explicitly promotes them to a shared processing object; visual coincidence never changes ownership.

## Workbench frame and density

The composition view is a Bitwig-style frame that fits the viewport: a collapsible left inspector, the **Stage** (a dock of tabbed panels), and an optional settings column on the right, over a status bar. The Stage is the shared `DockStage` (`src/components/Stage/dock`) rendering the active **workspace**: a split tree of named dockers (Canvas or Desk on top, `Detail` [`node-detail`, `data-block-editor`] and an empty `Tools` strip below by default). `SplitStage` and the fixed top and bottom panes are gone (W-43). The inspector and settings column are regions outside the Stage; the Stage measures its own box (`layout/useStageBoxRem.ts`, with a 80 by 40 rem fallback before a real measurement, which jsdom never gets).

**Workspaces** (`layout/workbenchWorkspaces.ts`, `layout/workbenchPanels.tsx`; W-42). The center's layout is per project data: one `WorkspaceStore` JSON value under `compositionStateKeys.workspaces` (`hrifa.composition-workbench.ui.workspaces.v1`), read and written by the page with `usePersistentState`, listed in `unrecordedStateKeys` so layout changes are never undo steps. ### Node device layout: panel versus inspector

A node's controls are split by how often they are touched. **Shaping controls** are the ones changed repeatedly while listening or looking (generator patterns, mode, coefficients, the candidate picker, the Play/Stop buttons) and stay in the node's panel next to its result. **Setup controls** are set once or wire the node up (input sources, grid, preview sounds and volume, interpretation, and the output summary) and go to the left inspector's Node part. Quick test: if you would change it mid-listen, it is a shaping control.

A converted node renders `NodeDevice` (a header with the run buttons, shaping controls on the left, the result on the right, a one-line footer; each region scrolls on its own so a node never makes the page scroll) and wraps its setup controls in `NodeInspectorContent`. That component portals into the inspector slot because nodes keep all their state in their own hooks, so nothing is lifted out. It renders only for the active node, and falls back inline in the panel when the inspector is hidden so a control is never unreachable. Long lists inside the result use a fixed-height scrolling box (`.candidateList`). Interference, Householder, Fractioning, Pair composition, Arithmetic, Scale construction, Scale evolution, Pitch list and Melodicization are converted (`NodeOutputsSection` renders the Outputs part, and `GeneratorPairControls` is the shared a ÷ b input); only Mixer still uses the older stacked `NodeShell` layout and should follow the same split.

Control density comes from `compactTheme.ts`, merged into the app theme with `MantineThemeProvider` around this page only: smaller default sizes for buttons, inputs, badges, switches and action icons, and tighter default radius. It sets component defaults only, so colours and every other page are untouched, and a component that passes an explicit `size` keeps it.

Corner radius is defined once, in the `.workbench` class on the page root (`CompositionWorkbench.module.css`): it sets `--radius-control`, `--radius-panel`, `--radius-hairline` and Mantine's `--mantine-radius-default` from one `--workbench-radius`. A nested theme provider cannot change Mantine's CSS variables, which is why the radius lives in CSS and not in `compactTheme.ts`. Workbench styles must use those variables: stylelint (`.stylelintrc.json`, scoped to `src/pages/composition-workbench/`) rejects any `border-radius` that is not `0`, `inherit` or a `var(--radius-*)`. Menus and other Mantine portals render outside the root and keep the app's default radius.

Inlets sit on a card's top edge and outlets on its bottom edge, as in Max, Pd and OpenMusic, so signal reads top to bottom. Each port carries an invisible React Flow handle at its outer tip. Until the browser has measured a card, estimated handle positions keep cables drawn roughly right; once measured, the real positions win (the estimates are dropped from the node, otherwise every re-render would reset them).

Node cards have a fixed width (`NODE_WIDTH`) and size their height to real content rather than a guessed fixed height: the title, subtitle, footer, and port rails are laid out in normal flow (not absolutely positioned), so a node with inlets (e.g. Melodicization) is naturally taller than a source-only node. Wheel scrolling pans the page, not the canvas; hold Ctrl or Cmd to zoom with the wheel.

Inlet and outlet port badges sit flush against the card's top and bottom edges with no gap, and are squared on the side touching the card (rounded only on the outward-facing corners), so a card and its ports read as one fused unit — like merlons on top of a castle wall — rather than separate floating chips.

Only the node title is bold. Subtitle, footer, and port badge text are all regular weight; boldness is reserved for identifying the node itself.

A card's footer is quantitative and appears only when it can name one representative fact: a single-output node shows `type | count` (e.g. Pitch List's `Pitches | 5`). A node with multiple named outputs (e.g. Interference's resultant plus its generators) leaves the footer blank rather than picking one output as though it were authoritative or restating the outlet count the port badges already show. Regardless of output count, the footer switches to reporting incompleteness or a packet warning when one exists, rendered as a filled bar using Mantine's `--mantine-color-red-filled` background with `--mantine-color-white` text — colored text alone on the panel background read as too low-contrast to register as needing attention.

## Melodicization

Melodicization is the first explicit rhythm-and-pitch combination operation. Its rhythm input must be `list | duration | inter-onset`; its pitch input accepts `list | pitch | pitch-material` or `list | pitch-class | pitch-material`. Pitch-class material receives an explicit register floor and ascending-close voicing in the selected input route before Melodicization evaluates. Those route settings remain visible, bypassable, persistent, and provenance-producing; Melodicization itself still consumes concrete pitches.

Any rhythm inlet — not just Melodicization's — applies the same route-level "Interpret as rhythm" opt-in that pitch inlets already use for `readAsMidiNotes`. A connected source that isn't already `list | duration | inter-onset` (Arithmetic's output, for instance, never carries a role) passes through unconverted until this is explicitly turned on. Turning it on only succeeds for a bounded, honestly-numeric set of domains — `integer`, `rational`, `duration`, `onset`, `interval`, `cycleLength`, `pulseCount`, `phaseOffset` — and only when every item is already a bare, finite, positive number; pitch/pitchClass/note material and any grouped (chord-shaped) value are refused rather than guessed at. A refusal reports why as a packet warning instead of partially converting or silently discarding the offending items, and the connected inlet's own error remains the visible symptom until the toggle is turned on or a valid source is connected.

One source pulse is interpreted through an explicit musical duration such as a quarter, eighth, sixteenth, or thirty-second note. The operation accumulates those exact rational durations into note onsets and emits `events | note` with an exact musical frame. Tempo and display meter belong to preview realization and notation; changing them does not rewrite the note-event packet.

Pitch allocation is a named policy. Each pitch group consumes one rhythmic attack, regardless of how many pitches it contains:

- `cycle` repeats the pitch-group list across the rhythm spine.
- `cycle-rhythm` repeats the rhythm spine until every pitch group has played once.
- `zip` stops at the shorter input and reports the unused material rather than silently discarding it.
- `cartesian` plays every pitch group at every rhythm slot, one after another: both cycles run together, attack *k* takes rhythm *k* mod R and pitch group *k* mod P, and the pitch side steps once each time the cycles realign. The result is R × P attacks (4 attacks and 5 pitches give 20) laid out as successive rhythm cycles, not a stack of simultaneities.

A rhythm's rests and ties are resolved first (`rhythmAttacks`): a rest makes no event and takes no pitch, a tied run is one event whose `interOnset` and sounding length span the whole run, and the allocation modes count attacks rather than rhythm items. Articulation scales sounding duration from 1% through 200% while preserving each inter-onset duration. Every event retains its pitch array, inherits the rhythm and pitch-group provenance, and appends the melodicization parameters that created it. The shared audio compiler expands the group into simultaneous renderer voices only at the realization boundary.

Melodicization presents those events through the shared Shell `PianoRoll` component. The component receives display-neutral note rectangles (`start`, `duration`, and `pitchMidicents`) plus explicit bar and beat lines, so future nodes can reuse it without depending on Melodicization packets or Tone.js. It provides a Bitwig-style scrollable viewport, independent time and pitch zoom, adaptive subdivisions, note fitting, a pinned keyboard and ruler, and an optional page-following playhead. Microtonal values retain fractional vertical placement rather than being rounded to MIDI semitones. The exact event table remains available as a secondary inspector.

## Arithmetic

Arithmetic ports OpenMusic's core numeric functions (`OM+`, `OM-`, `OM*`, `OM/`, `OM//`, `OM^`, `OM-E`) as one node with an operator selector, verified against OM 7.6's own reference documentation rather than assumed. All seven share the same two-inlet (A, B) shape except `eˣ` (OM-E), which is unary; `eˣ` ignores B and its own inline fallback entirely, and the node hides B's input control accordingly. A and B each accept a routed connection or, when unconnected, a typed-in fallback number seeded from that operator's own OM-documented default argument value — an unconnected inlet still produces a fully specified result, exactly as it does in OM itself.

Plain-number domains (`integer`, `rational`, `duration`, `onset`, `interval`, `cycleLength`, `pulseCount`, `phaseOffset`) are offered as A/B sources directly. `pitch` and `pitchClass` are also offered: a pitch group's bracketed pitches (a chord) are exactly the kind of nested list OM's own arithmetic recurses into — verified against OM 7.6's kernel.lisp, where `om+`'s list+list method is a CLOS-dispatched `mapcar` with no special "list mode," so a leaf number broadcasts across every pitch in a group and two groups pair up the same way two top-level lists do. `note` is the one domain excluded: its items are full event objects (onset/duration/velocity), not a number or a group of numbers, so there is nothing to decompose.

A and B are never required to share a domain. OM's `om+` has no concept of domain at all — it dispatches purely on Lisp type (number vs list) and combines whatever it's given. When A and B's domains agree, the result keeps that meaning (e.g. two `duration` lists stay `duration`); when they disagree, the result's domain falls back to a neutral `integer` rather than silently claiming to still be whichever domain happened to be A's — the packet stays honestly typed even though what it now represents is up to whoever connects it next. A grouped side's structure survives a mismatched combination too: a one-pitch group added to a plain number still comes out as a one-element array, not unwrapped to a bare number, matching Lisp's own `(om+ 1 '(60)) => (61)`.

Combination follows OM's own documented broadcasting: a scalar broadcasts over a list unambiguously, and two equal-length lists always pair elementwise. Only when A and B are both lists of *different* lengths does the node ask which alignment policy to use, reusing Melodicization's same `cycle` / `cycle-rhythm` / `zip` / `cartesian` vocabulary (relabeled generically, since A and B are symmetric operands rather than a rhythm-anchored spine). Divide and floor-divide by zero report a warning and produce `Infinity`/`NaN` rather than aborting the packet, matching how Melodicization's Zip already reports unused material instead of refusing to run.

The node also shows the raw numbers actually being combined (`A raw` / `B raw` / `Result raw`), decomposed via the exact same function the computation itself uses (`rawNumericTree`), not a separately re-derived display value — so what's shown can never silently drift from what's really happening, and a route's hidden defaults (like a pitch-class register floor) are never invisible.

Pitch-class connections default to staying raw pitch-class (`voiceAsPitch: false` on the route's Quick Adjust) rather than being silently voiced into a concrete MIDI register — a route stays connected and transpose/invert/retrograde/rotate still apply, but nothing forces a register floor unless the user explicitly turns it on. Consumers that require concrete pitch, like Melodicization, need that flag on for that specific route.

An optional modulo post-process — a toggle plus divisor, applied to the node's output after the arithmetic operation — is a reusable building block (`moduloTreatment.ts` + `ModuloControl.tsx`) rather than something inlined into Arithmetic specifically, following the same shared-component precedent as `VolumeControl.tsx`.

## Swirling Mists

Swirling Mists (`mist.ts`, `SwirlingMistsNode.tsx`) is a source node: layered looping waves (strata) sampled into plain numbers. It has no inlets. Design notes and what it replaced are in `SWIRLING_MISTS_SPEC.md`.

- **LFO model, one axis.** Each stratum is an LFO with two layers. Its shape is one pass of a waveform: `cycles` whole cycles of it per pass (a sine with 2 has two peaks), a `phase` (fraction of a pass), and an `amplitude` around a `center`. Its `speed` is how fast the pass is traversed, in passes per position, so a bigger number is faster: speed 1 does one pass per position and 0.5 does half of one, so speeds 1 and 0.5 line up every 2 (two passes of one, one of the other), and speeds 2 and 3 every 1 (two passes against three). There is no other time control. With `u = phase + speed · s` passes elapsed at position `s`, `value = center + amplitude · shape(u · cycles)`, the shape repeating every 1 and held in [-1, 1]. A speed of 0 holds the stratum at its phase and a negative speed runs the pass backwards. A sine is computed directly (smooth at any speed); a random walk (`walkPoints` per cycle, seeded, bridged so it has no seam) and a drawn curve are tables. The speeds make strata drift against each other, and the shapes do not change when the strata realign. The retired lens had a second coordinate `x` that added to the same phase, and a per-stratum loop in cells that doubled as the table resolution (so a 2-cell sine was flat); both are gone. A field-wide "loop length" was tried and removed: the extracted values depend only on the ratio of stride to it, so it duplicated Stride. Settings carry a `version` (4, speed in passes per position); stored settings of any other version are not accepted and fall back to the defaults.
- **Sampling.** Stride and Steps decide where samples are taken, in positions; speed 1 is one pass per position, so the default stride of 1/16 over 16 steps samples one pass of a speed-1 stratum. Samples per cycle is `1 / (speed · stride · cycles)`, and a cycle shorter than two strides is reported as aliasing.
- **Outputs.** `chords` is `list | integer` whose items are groups, one per sample step with one value per enabled stratum. `voices` is `bank | integer`, one list per stratum. Both carry `sample-mist` provenance. A non-integer rounding step makes the domain `rational`. Interpretation stays downstream: a pitch inlet's "read as MIDI notes", a rhythm inlet's "Interpret as rhythm", or Arithmetic.
- **Output range.** The field's theoretical reach (`center ± amplitude` over the enabled strata) maps onto the low–high range and rounds to a step, so values do not move when steps, start or stride change. Disabled strata are left out of the outputs.
- **Extracted snapshot.** Under the live view's controls, `MistSnapshot` shows exactly what the outputs contain: one column per sampled step (Steps, Start, Stride), one dot per stratum in it, on the output range (the same value axis as the NOW slice, but rounded as the outputs are). A line joins each stratum's dots, which is its voice, and a column read downward is one chord. Hovering a column reads out its unit and values. The live view is independent of it, so the snapshot does not move while the field runs. While the audio preview plays, a red playhead sits on the step that is sounding and its dots grow (`playingStep`, from the engine clock: step k sounds at k × the preview step length), and the readout names the playing step.
- **Repeat length.** The badge shows the least common multiple of the strata's pass lengths (1 ÷ speed) in positions `s`, the same idea as Mixer's realignment period. Speeds 1 and 0.5 repeat every 2, speeds 2 and 3 every 1, and 1, 1.25 and 1.5 every 4. It is computed in exact integers (`mistRepeat`): each speed is a simple ratio or the decimal as typed (up to 12 places), and with speeds n/d the repeat is lcm(d) ÷ gcd(n). There is no cap on the repeat or on the precision, so speeds 0.7133, 0.7134 and 0.7135 repeat after 10000 units (7133 : 7134 : 7135 passes) and 0.71335 and 0.71337 after 100000. The badge also shows the passes each stratum completes per repeat (6, 7 and 50 repeat every 1 with 6 : 7 : 50), since a whole-number repeat of 1 says nothing about how intricate the pattern is. A speed that is not an exact ratio (π) has no repeat, and one too large for an exact fraction shows as a plain number. Shapes do not affect it (a sine with several cycles may repeat sooner, but the passes always realign here).
- **Persistence.** Only the settings object, preview step, gate and volume persist; tables and samples are rebuilt. The seed is part of the settings, so the same settings reproduce the same walks.
- **Live view.** `MistStage` runs the field on its own clock, independent of audio and of the sampling window (Steps, Start and Stride only decide what the outputs contain; that sampling window shows as a thin bar under the plot, once per repeat, and nothing is drawn through the curves). Run advances a position by `speed` per second on a requestAnimationFrame loop; the curves scroll past a fixed "now" line (35% across), so the past leaves on the left and the future arrives on the right. To its right in the same SVG is a vertical slice at now: each stratum is a dot at its unrounded mapped value on the output range, so strata read against one another (labels spread apart so they never overlap). Each curve is drawn with several points per cycle in view (at least 360, at most 2000), because a fixed number of points lands at nearly the same phase of consecutive cycles when its spacing is close to a cycle's length and draws a slow wave that is not in the data. When the cycles are too packed to tell apart (under 4 plot units each) the row is drawn as a translucent band spanning its amplitude and labelled with its cycle count; zoom in with a smaller View span to see the wave. Each row is labelled with its period (`loop / |speed|`) and ticks where its loop restarts. Dragging the plot pans through time. When the field repeats, every number shown wraps at the repeat length (the left, now and right labels, and the Position box), a cycle counter reads "cycle n · position of repeat", and a dashed "cycle n ↻" line marks each repeat boundary; the position itself stays unwrapped internally, and the picture is continuous across the boundary because the signal is periodic. Fields with no repeat count up without bound. The view span defaults to one full repeat of the field (Fit repeat), and can be set to any positive value and the speed to passing the shortest period in about two seconds; both are overridable and persisted. When the audio preview plays it drives the same position from the engine clock (`engine.clock(instanceId)`, as `Playhead` does) at `start + elapsed / step · stride`. `buildMistField` evaluates the field at any position, and `sampleMist` uses the same field.
- **Drawn curves.** A stratum's waveform can be Draw: `custom` holds one cycle as 64 values in [-1, 1], read directly (tiled by `cycles`) with the last point leading back into the first. A new drawn curve starts as a sine, so switching never changes the sound. `CurveEditor` (in a modal) edits it by dragging, filling skipped columns with a straight line, and offers starter shapes, smooth, invert, reverse and shift. Saved settings without `custom` still load.
- **Preview.** Plays each step's chord as MIDI notes through `createPitchPreviewPlan` with its own step length, like Pitch List, once through the window (no looping). There are no custom tables from text, keyframes or 3D view.

## Where a rhythm starts

An inter-onset list says how far apart attacks are, not where the first one falls. That lives in the frame's `origin`: the first attack's position in frame units, measured from the downbeat (`rhythmFrame.ts`). Origin 0 is a downbeat start. In a cyclic frame `0 ≤ origin < cycle`: the durations still sum to the cycle, and the last one wraps into the next cycle's first attack, so a loop starting on pulse 2 sounds its first two pulses as the tail of the previous cycle. In a linear frame, origin is a leading rest and `extent = origin + Σ durations`.

- Rhythm routes have a **Start offset** Quick Adjust, in pulses after scaling. It wraps in loops; in a linear frame, starting before the downbeat is clamped with a warning. Retrograde and rotate reorder durations and keep the first attack at the rhythm's start. Duration scale scales the start along with the durations. Routes saved before offsets existed read as offset 0.
- Melodicization shifts every attack by the start; bar lines do not move, which is what places the attacks off the beat. Duration previews play the leading silence.
- A bank whose entries start in different places lists them in `metadata.entryOrigins`, and selecting an entry gives the resulting list that entry's start.
- Output summaries show `starts +n` for a rhythm that doesn't start on the downbeat.

## Rhythm realization

Status: implemented in `rhythmRealization.ts`. Interference, Fractioning, Pair Composition and Rhythm Householder previews all realize through it (`createRhythmPreviewPlan`, `createInterferencePreviewPlan`), and Mixer compiles `materialFromRhythmPacket` against the same function. Rests and ties are carried by packets (see "Rests and ties" below) and resolved here.

**Principle.** A rhythm packet is data in its own unit (usually pulses). Realization is the one explicit step that gives it musical time, a voice, and an articulation. This follows OpenMusic's split between a rhythm and the container that interprets it: an RT carries proportions, while the container's `Qvalue` (an abstract unit, 1/qvalue of a quarter note) and `QTempo` give those units a physical meaning. Here the equivalents are the transport's pulse value and tempo. Tempo is never part of the realization; the engine's timeline resolves it.

**Contract.** One pure function turns a rhythm packet into musical-time events:

- **In:** a `list | duration | inter-onset` packet (with its frame), the musical duration of one pulse (from the transport's pulse value), a resolved voice (`layerSound`), and optional channel parameters: start offset and gate.
- **Out:** events with exact rational `at` and `duration` in quarter notes (`MusicalPerformanceEvent`), a `busId`, and provenance pointing back to the source items. A `MusicalPerformancePlan` is built from them.
- **Frame.** `origin` becomes a leading offset, in pulses mapped through the same pulse value. A cyclic `extent` is reported as the loop length but never unrolled here. Unrolling to a horizon, and the loop policy that governs it (`free`, `restart with longest`, `once`), belong to whoever compiles several sources into one plan (Mixer), not to this function.
- **Not in the contract:** tempo, metronome, count-in and looping. Those belong to the transport and the engine.

**Gate.** Gate sets how long an event sounds as a percentage of the time slot to the next attack, from 1% through 200%, as in Melodicization's articulation and Pitch List's gate. It is a realization parameter, never part of the packet. OpenMusic likewise keeps legato on the playing object (chord-seq), not in the rhythm. The default is 95%: connected but not blurred, like a pianist's legato where each note releases just before the next attack. Percussive voices decay on their own and barely depend on it, while sustained voices (`tone`, sine) need a musical gate so their length scales with the pulse. The old fixed 0.12 s cap has no musical equivalent and is not carried over. A gate applies to the whole sounding span of an event, which for tied notes is the full tied length.

**Rests and ties.** Inter-onset lists carry silence and continuation in the packet, following OpenMusic's rhythm tree (a negative number is a rest, a tie continues the previous note) with one change JavaScript forces: `1.0 === 1`, so a tie is an explicit flag.

- **Fractional lengths.** A duration is a pulse count and need not be whole: `6/5` is a valid length (typed as a fraction or decimal), held as an ordinary number and recovered exactly with `rationalFromNumber` (continued fractions, denominators up to 10^6). `rhythmAttacks` sums attack positions and slots as exact rationals, and Melodicization, Mixer and the realization turn them into musical time from those, so a rhythm scaled by 3/5 plays on exact onsets, not rounded ones.
- **Rest:** a negative duration. Its magnitude is the length of silence: `-2` is a two-pulse rest, typed `r2`. It consumes time like any other item and produces no event. A rest takes no pitch in Melodicization.
- **Tie:** `DataItem.tie`, on inter-onset lists only, set on the item that *starts* the tie and meaning "tied into the next item". Typed `2~`. `2~ 1` therefore plays as one three-pulse event, exactly as `3` would; the tie keeps the two-slot structure for display and for operations that act item by item. Putting the marker on the starter (the LilyPond and ABC convention; OpenMusic marks the continuation) makes parsing local to the token and means reordering needs no special case: every item keeps its own marker through rotation and retrograde.
- **Dangling ties.** A tie into a rest, or off the end of a linear rhythm, has nothing to continue: it is reported and ignored. In a cyclic rhythm a tie off the end wraps and the first item continues the last event (so a loop sounds that first item as the tail of the previous cycle's last event, and a single pass leaves it silent). `rhythmAttacks(steps, origin, { cyclic })` resolves all of this.
- **Operations.** Rotation keeps each item with its marker. Retrograde reorders the items and each marker travels with its own item, so `1 2~ 3` becomes `3 2~ 1` and `1 2 3~ 4` becomes `4 3~ 2 1`: the item still ties into whatever follows it, which is not the neighbour it was tied to before. Duration scale multiplies rests by magnitude and keeps their sign. A frame's `extent` is Σ|d|, and rests and ties both count.
- **Notation** (`rhythmNotation.ts`): items separated by spaces or commas; `3`, `r2`, `2~`. A rest cannot be tied. `parseRhythmText`, `formatRhythmText` and `rhythmItemNotation` are the one reader and writer.
- **Compatibility.** A rhythm with rests or ties is not interchangeable with a plain duration list. `compositionOutputOptions` does not offer it to a consumer unless that consumer passes `allowRestsAndTies`; today only Melodicization (rhythm inlet) and Mixer do. Arithmetic, Rhythm Householder, Scale Evolution and the rest never see such a rhythm rather than dropping its ties or reading a rest as a number. A consumer opts in only once it handles both.
- **Authoring.** The Rhythm List node types a rhythm directly (`3 r1 2~ 2 1`) with a Loop switch that sets the frame to cyclic or linear. The Rhythm Edit node (`rhythmEdit.ts`) edits any connected rhythm the way the Grid Traversal workshop programs a piece. A **program** is a cyclic list of blocks `[action,count]`; the count says how many notes the block covers and can be `n`, a variable that starts at a value and changes by a step after every K completed blocks (never below 1). A program has a **phase** (notes that pass before it starts) and a **rate** (it ticks on every R-th note; the rest pass through), exactly as a field program does there. Two programs run independently: a **structure** program (`x` keeps a note, `r` makes it a rest of the same length, `~` ties it into the next note, `u` removes a tie; `[x,2][r,1]` keeps two notes then rests one, and a bare `x x r` is the same with every count 1) and a **length** program that changes each note on its own (`o` leaves it, `*3/5` multiplies it, and a bare fraction does the same, so `3/5` and `*3/5` agree and `/2` divides (a bare whole number or decimal is not a multiplier: write `*2` or `*.6`), `+1` or `-1/2` adds or removes pulses, `=2` sets it). **Rules** remain as the other way to choose notes: one per line, a selector (`3`, `4-6`, `1,3,5`, `every 3 from 2`, `first`, `last`, `all`, `>2`, `<=1` by length) and an action that is either a structure action or a length action; later rules override earlier ones and the programs. Lengths are exact fractions, so `2 * 3/5` is 6/5 of a pulse. A tie into the last note of a linear rhythm, or a length that would reach zero, is reported and left as it was; the frame's extent is recomputed from the new lengths and what happens to a grouping when lengths change is the node's "When lengths change" choice: **drop** it with a warning (the default), **keep** its boundaries at the same pulses even though notes may then cross them, or **move** each boundary with the note it falls in, to the same fraction of that note's new length (exact), so a boundary at the start of note 4 stays at the start of note 4 and groups become unequal (`units` is rescaled by the change in total length). An empty program or rule list changes nothing, so each part works on its own, and the node accepts rests and ties on its own inlet so edits can be chained. The node draws the input and the edit on one pulse scale with a curve per note edge between them (color for direction and change from the original position, cyan to orange; opacity for the shift as a share of the whole rhythm, full at a tenth of it; thickness from 2px to 8px by rank within this edit, so its furthest-moved edge is always the 8px one), and a third strip, the input scaled note for note by one exact factor to the edit's overall length (`scaleStepsToLength`), which separates what the edit did to the shape from how long it made the whole. The whole diagram (program tracks, input, curves, result, scaled original) is one canvas that scrolls sideways when the shortest note would be under 30px, with row labels pinned left, a zoom bar under it in the style of Bitwig's overview bar (its thumb is the part in view: drag it sideways to scroll, up or down to zoom, or drag either end to change how much is shown with the other end fixed; click the track to move there; arrow keys scroll and zoom) replaces the roll's own scrollbar, and a zoom control (−, +, Fit, Reset) changes only the horizontal scale, as the width of the shortest note, so row heights never change and the middle of the view stays in place, and "Follow playback" scrolls it with the playhead: centered as a DAW does (the view stays put until the playhead reaches its middle, then keeps it centered, stopping at the end of the content), a page at a time as the piano roll does, or off. Preview plays any combination of the input, the result and the scaled original together, each on its own rhythm voice (primary, secondary, tertiary) unless overridden, as Rhythm Householder does for its A/B. Rests and ties inside Interference's own generators are not built.
- **Relation to start offset.** `frame.origin` and a leading rest describe the same silence. A cyclic frame keeps `origin` because the wrap-around semantics differ (see "Where a rhythm starts").

## Mixer

The Mixer auditions several ideas together: a preview layer one step before a committed arrangement, not a timeline. It is a sink. It publishes no outputs and, for now, no `layers` packet; what a committed multi-stream packet should be needs more thought.

- **Channels are its inlets.** The receiver's route state is the single source of truth for which channels exist and in what order. Each channel is one port with a stable id (`ch-…`, never a display index), shown as `Ch 1`, `Ch 2` by position. Adding or removing a channel adds or removes a route binding; its persisted settings (`mixerChannels`) are pruned to match. Because route bindings are ordinary, each channel gets Quick Adjust (a rhythm channel's retrograde, rotate, duration scale and start offset) before it is mixed.
- **What a channel plays.** An `events | note` stream plays directly; an inter-onset rhythm is realized on a rhythm voice through the shared rhythm realization (voice by channel position unless overridden, gate default 95%). A numeric list must be explicitly interpreted as rhythm on its route; a pitch list has no rhythm and is reported, never guessed at.
- **Loop policies** (`mixer.ts`, per channel): `free` repeats at the channel's own period, so together the free channels repeat every least common multiple of their periods, the realignment period (the meta interference pattern); `restart with longest` cuts and restarts together at the longest looping cycle's end; `once` plays a single time. A start offset rotates a looping channel (as cyclic `origin` does) and delays a one-shot. The realignment period is shown beside the node.
- **One plan, one transport start.** Play compiles every channel into a single musical-time plan with the mixer's instance id as `sourceId`, so channels stay phase-locked, and loops it (`PlaybackRequest.loop`) when it is exactly one period of the pattern. A realignment beyond the horizon (128 bars of 4/4) or an oversized event count is truncated or refused with a warning, not unrolled silently. A truncated mix is flagged (`truncated`), plays once without looping, and is captioned in the node as a preview: the "realigns every" badge still reports the true period, but the progress bars measure progress through the preview, not toward the true sync.
- **Composite roll.** The shared `PianoRoll` draws every event of the compiled plan (`mixerRoll.ts`), each note colored by its channel (a note may carry its own `color`; the channel hue follows its position and never uses the red of the playhead), so the roll shows what will be heard, including loop repeats. Rhythm channels sit at their voice's sounding pitch, which makes the roll a piano roll and a percussion roll at once. Past 4,000 events it draws a sample and says so. The playhead follows the engine's clock and wraps at the pass length while looping, so every channel's hits line up against one moving line. Each channel header shows its kind, event count and length in pulses and bars.
- **Per-channel rolls.** A toggle switches the roll from the composite to one roll per channel, each showing that channel's own cycle (rotated by its offset, or delayed for a one-shot) with its own playhead, as a DAW's launcher shows them. All channel rolls share one time scale, so a short cycle is visibly shorter than a long one; each channel roll fits its own pitch range. The scale fits the longest channel roll by default and can be zoomed. Each channel roll's playhead is derived from the mix's position within its pass: a free channel wraps at its own period, a restart-with-longest channel resets at each block of the longest cycle, a one-shot runs once and holds. Each looping channel also has a progress bar (on its channel roll, or at the top of its strip in the composite view) that fills across the whole pass from one sync point to the next, with a tick at every cycle boundary: every channel fills at the same rate, and what differs is where its ticks fall (a free channel ticks at its own cycles, a restart-with-longest channel at its restarts; a one-shot has no bar). While playing the header reads "cycle 5 of 15", and the toggle row shows the pass count. Pure helpers: `mixerChannelRoll`, `channelRollView`, `channelPlayhead`, `cycleProgress` in `mixerRoll.ts`.
- **Levels.** Each channel has its own bus. Level, mute and solo are live and combine with the master fader; the loop policy, offset, gate and sources apply on the next Play.

## Rhythm Householder

Rhythm Householder (`householder.ts`) alters a rhythm along a chosen bias axis while keeping its attack count and total span. It takes a rhythm inlet (`list | duration | inter-onset`, with the usual route-level "Interpret as rhythm") and an optional numeric `axis` inlet. It publishes `selected` (an ordinary inter-onset list) and `candidates` (`bank | duration | inter-onset`, one durations array per entry), both keeping the input frame. Attack j of a candidate inherits the provenance of input attack j, since both modes keep attack order.

- **Reflect** works in duration space: `d' = d + (c − 1)(q·d / q·q)q` with the axis `q` centered so `Σq = 0`. `c = −1` is the exact Householder reflection, `0` removes the component, and `1` is the identity. The total is preserved by construction, and every component orthogonal to `q` is untouched. Presets: trend (index ramp), swing (alternation), arch (parabola), a custom contour, or a routed list, which takes precedence. When the exact reflection would push a duration below the minimum, the node uses the nearest valid rhythm (a simplex projection) and reports the realized coefficient. Rounding to the grid uses largest-remainder rounding, so the total stays exact. Note that a palindromic rhythm, such as any interference resultant, has no trend or swing component: reflecting it along those axes is the identity, and the node says so.
- **Metric** works on onset slots: each enabled axis (a repeating per-slot accent pattern, or early/late position) is centered over the span, and its bias is the sum at the attack slots. The target is `c ×` the input bias, clamped to the reachable range (with a warning). The score is the weighted, range-normalized distance to each target, plus a "keep identity" penalty and a "stay close" penalty. Keep identity measures the share of attack pairs whose distance changed, using the rhythm's interval content (the rhythmic analogue of an interval-class vector, wrapped around the cycle in cyclic frames). It therefore favours displacing the whole rhythm over reshaping it: a rotation moves every attack but changes no interval. Stay close penalizes attack movement directly. Because single-attack moves can never reach a rotation, local search scores every attack rotation and also descends from the best few. By default the start is free: candidates may begin anywhere in the frame, and each candidate's start travels with it as the output's `origin`. Loops are also seeded with every time-shift of the input, which is classic displacement. "Keep the start where the input's is" pins the first attack instead. The search is exhaustive up to 100,000 attack sets and local search from the input beyond that, and the node reports which one it used.

This replaces a C# prototype whose greedy search barely depended on the input rhythm, whose flips cancelled out in the scoring, and whose reflected onset field was dominated by the input's own spikes.

## Node runtime (`runtime/`)

How the page hosts nodes, since R1 (2026-11-18). Behavior is unchanged; the plumbing moved out of
`CompositionWorkbench.page.tsx`.

- `outputStore.ts` is a pure external store of every node's published outputs (`publish`,
  `prune`, `get(ref)`, a `list()` array whose identity changes only when an output really changes,
  `subscribe`). The equality rule is the old one: same keys and the same `packet` and `label`
  objects means no change. `useOutputs.ts` reads it with `useSyncExternalStore`.
- `nodeRegistry.tsx` is the one table keyed by node id: `stateKeys`, `ports` (from
  `nodePorts.ts`, plain data the canvas also reads; the mixer's empty list means routed), `takesOutputs`
  and `render(props)`.
- `NodeInstanceHost.tsx` is a `React.memo` host per placed node: the hidden-unless-shown div, the
  `NodeActiveContext` provider and the registry's element. Only a node with `takesOutputs` subscribes
  to the store, so a publish re-renders the page and the routed nodes (those that read outputs), not the source nodes.
- **State store (R3a, done).** `stateStore.ts` (pure TS) owns every `usePersistentState` value in one
  keyed map: current value, last raw JSON, config (`fallback`, `accepts`, `migrate`), listeners and ONE
  history applier registered by the store (`registerHistoryApplier`) when the key is first used.
  `usePersistentState` keeps its signature and is a thin `useSyncExternalStore` hook over it (a stable
  `set` per key; a mount effect persists the initial value). A key stays alive after its
  last hook unmounts, so undo and redo reach a node whose view is not mounted, and two hooks on one
  key share one value. Storage writes happen in `set` (skipped while `isReloading()`, as before).
  Release: when the last hook of a key unmounts and its storage entry is gone (the page's delete
  removes the node's stored keys and records them, so undo writes storage first and the remount
  reads it), the store drops the key and its applier. A key with no hook is re-read from storage when
  storage changed under it (tests, a stale entry); opening a project reloads the page, so the store
  starts empty. `history.ts` is unchanged.
- **Evaluators (R2, done).** A ported node has a pure `evaluate(state, inputs, ctx)` in
  `runtime/evaluators/<node>.ts` returning `{ outputs, ...whatever its display reads }` (no React,
  storage or `window`). Ported so far: Pitch List, Rhythm List, Arithmetic, Fractioning, Pair
  Composition, Scale Construction, Scale Evolution, Interference, Swirling Mists, Rhythm
  Householder, Rhythm Edit, Melodicization, Data-block source (every node that publishes outputs;
  the Mixer publishes none). `nodeEvaluators.ts` is the non-React table by node id;
  `nodeRegistry.tsx` lists the same function as the entry's optional `evaluate`. Since R3b the
  node's runner (below) calls `useNodeEvaluation(nodeId, state, inputs, ctx, publish)`
  (`useNodeEvaluation.ts`), which compares state, inputs and ctx field by field, runs the
  evaluator once per change and publishes in one effect; the node view never calls it and has no
  publish effect of its own. Each evaluator is split into `compute` (no
  label; the packet and display values) and `outputs` (wraps the packets with `{ ref, label }`), so
  a rename keeps every packet object and only the labels change. Components import the hook and
  the evaluator file, never `nodeRegistry.tsx` (it imports the components). **Inputs must keep their
  identity when unrelated outputs change**: a node that reads outputs passes only what it reads
  (Arithmetic: `pickArithmeticInputs` returns the two bound outputs and bindings; Scale Evolution:
  `pickScaleEvolutionInputs` returns the bound `sequence` output and binding; Householder:
  `pickHouseholderInputs` the `rhythm` and `axis` outputs and bindings; Rhythm Edit:
  `pickRhythmEditInputs` the `rhythm` output and binding; Melodicization:
  `pickMelodicizationInputs` the `rhythm` and `pitches` outputs and bindings; Data-block source takes
  the desk's own data-block object, which keeps its identity until the data-block is edited), otherwise its own
  published output would re-trigger its evaluation forever. `compute` takes an optional per-instance
  memo (`runtime/memo.ts`, `memo(key, deps, fn)`, one per hook instance) so a part of the output
  rebuilds only when its own deps change, as before the port (a root change rebuilds the pitch
  classes, not the sequence or stage packets); without one, a fresh memo gives the same result.
- **What lasts and what is replaceable (W-45).** The runtime is not a commitment to today's nodes,
  packets or routing. Meant to last: the shape (a node is a pure function from persisted state,
  picked inputs and context to published outputs, run outside its view) and the pieces that carry
  it (output store, state store, runners, evaluation store, `memo.ts`, `useNodeEvaluation`). The
  output store treats a packet as opaque (identity and label only). Replaceable at will: the
  `DataPacket` shape, the port-based routing model and the `pickXInputs` helpers, every evaluator
  in `runtime/evaluators/`, the state specs, and the R2 evaluator tests (they pin today's behavior
  for a no-change refactor; they are not a spec, so rewrite them with a redesigned node).
- **Hidden views stay mounted (human, R3, 2026-11-18).** Views still own live state (playing
  previews, selection, scroll, open dialogs, playheads), so the `node-detail` panel keeps every
  node host mounted and hidden. The goal is the DAW model (playback and live view state outside
  the views, then unmount hidden views): BACKLOG `[workbench]` "DAW model for playback and view state".
- **Runners, state specs and the evaluation store (R3b, done; supersedes "nodes must stay mounted
  to publish").** Every placed node that has an evaluator is evaluated and publishes whether or not
  its view is mounted, by a headless runner:
  - `NodeEvaluationRunner.tsx` (`React.memo`, renders `null`) is rendered by the page, one per placed
    instance, OUTSIDE the Stage panels and before them (inside the settings and desk providers, because
    it reads `edo`, the transport pulse and the desk data-block). Per instance it reads the persisted state
    (`useNodeState`), the inputs, calls `useNodeEvaluation` once and publishes to the output
    store, then puts the evaluation in the evaluation store. `runnerBindings` in that file is where
    each node's inputs come from: routed nodes take only the picked outputs (`pickXInputs`, from
    `useOutputs` and the instance's route state), Data-block the desk data-block (`useDesk`), Pitch List an
    empty `upstream`, Melodicization `edo` and the transport pulse unit, and the others `edo` from the
    settings. A source node's runner subscribes to no outputs (`useOutputs(store, false)`), so
    another node's publish does not re-render it (R1's property). The Mixer has no evaluator and no
    runner.
  - `nodeState.ts` and `nodeState/<node>.ts`: the persisted fields an evaluator reads are
    declared once as a `NodeStateSpec` (per field: the base key from `compositionStateKeys`,
    `fallback` (a function gets the fields declared before it: Pitch List's default text depends on
    its format), `accepts`, `migrate`, `options`). `useNodeState(spec, instanceId)` returns
    `[state, set]` (`state` keeps its identity until a field changes, `set.<field>` is stable) over
    the same store keys `usePersistentState` uses (`compositionInstanceStateKey`: every instance, the default ones included, stores under `<base key>.instance.<instanceId>`), so the runner and
    the view register the same config. A view reads its evaluated fields through the spec and keeps
    plain `usePersistentState` for fields only it uses (volume, sounds, view toggles).
  - `evaluationStore.ts`: the latest evaluation per instance outside React (`put`, `notify`, `get`,
    `prune`, `subscribe(instanceId)`). The runner `put`s while rendering (no notify) so a view rendered
    after it in the same pass already reads the new value, and notifies in an effect. A view calls
    `useNodeEvaluationResult(nodeId, instanceId)` (a `useSyncExternalStore` reader, context
    `EvaluationStoreContext` from the page); there is exactly one evaluation per instance and views no
    longer take `onOutputsChange`. A view with no runner throws.
  - **Delete and release.** The page's delete removes and records the instance's stored keys, then calls
    `deleteState(key)` for each (`stateStore.ts`): the store drops the key and its applier and flags it
    deleted. A write to a deleted key is ignored: a late `set` finds no key, and a render that
    re-creates it (a hook not yet unmounted) holds a value in memory only (`detached`: no storage
    write, no history record). The flag clears when storage holds the key again (an undo's storage
    write) or when a hook mounts for it (`persistState`: a mounted hook means the instance is live).
    Undo of a delete writes storage, the instance returns, its runner mounts and reads the state back.
    The page also prunes the evaluation store on delete.
  - **Views still mount hidden.** `NodeInstanceHost` still renders every instance's view in
    `node-detail` (hidden unless shown, the panel `keepMounted`). Publishing no longer depends on it;
    unmounting hidden views was NOT done because it is user-visible: a playing preview stops, and a
    note selection, roll tool, scroll position, open Forte catalog and curve being edited reset (the list
    is in PROGRESS R3b). Removing the hosts is a separate decision.
- **Adding a node:** its id in `compositionWorkspace.ts`, one registry entry, and, for a node
  that publishes outputs, an evaluator file, a line in `nodeEvaluators.ts`, `evaluate` on the
  entry and a `.test.ts` that compares it with hand-computed expected outputs (default state, one
  edited state, a rename keeping every packet, and for a routed node an unrelated-output identity
  case).

## Adding a node with playback

The default for any new node that previews sound. Fractioning is the smallest complete example;
Rhythm Householder shows layered (A/B) playback. Two shared pieces do most of it:
`useNodePreview` (`useNodePreview.ts`) runs the preview, and `DurationStrip`
(`components/DurationStrip.tsx`) draws the numbered bar with its playhead.

1. **Timing comes from the transport.** Rhythm previews build a musical-time plan with
   `createRhythmPreviewPlan` and `transportRhythmContext(settings.transport)` (pulse value and
   timeline); `musicalPlanSeconds(plan)` gives the length for a status line. `pulseSeconds` remains
   only for drawing a playhead. Don't add a per-node tempo, unit, or meter control. Musical-time plans
   (Melodicization) use the transport's tempo, meter, and pulse value.
2. **Play through `useNodePreview`.** It stops the previous session, keeps the volume and any
   extra buses live, owns the status line (`preview.status`), and clears playing state on a global
   Stop. Pass `followTransport: true` for anything on the transport's pulse grid, so the metronome
   and count-in apply; leave it off only for previews with no pulse (Pitch List). Node-owned
   playback state (highlighted layers, a custom playhead) is cleared in `onEnd`.
3. **Sounds come from the voices.** Play layer *n* on `layerSound(settings.sounds.rhythm, n, override)`
   and give each layer a `SoundOverrideControl` with the override in the node's persistent state
   (default `null` = use the voice). Don't hard-code an instrument or pitch for a rhythm layer.
   Two layers you'd want to compare get an A/B button
   (`createRhythmPreviewPlan` with one layer each).
4. **Give the hook a `transportPlay`** for the main preview, so the header Play button and the
   space bar start it.
5. **Draw durations with `DurationStrip`** and pass `playhead={{ sourceId, unitSeconds }}`; it
   handles late starts and the playhead. With several strips, set `playhead.visible` for the ones
   actually sounding. For any other display (e.g. Interference's attack rows), add
   `<Playhead … />` as the container's **last** child (`durationBlock` colors alternate with
   `:nth-child`).
6. **Give the node its own volume fader** (the hook's `volume`, on the `preview` bus). The
   `meter`, `count-in`, and `grouping` buses are reserved for clicks.
7. **Use the node's instance id as the plan's `sourceId`.** The playhead, global Stop, and
   `stopSource` all find a preview by it.
8. **Store new persistent keys** in `compositionStateKeys` and list them as the node's
   `stateKeys` in its entry in `runtime/nodeRegistry.tsx`, so deleting the node clears them.
9. **Register the node in one place**: add its id to `compositionWorkspace.ts`, then one entry in
   `runtime/nodeRegistry.tsx` (`stateKeys`, `ports` if it takes routed inputs, `takesOutputs`,
   `render`). The page and the canvas need no change.

Global Stop (header button or space while playing) ends sessions without calling `onComplete`;
`useNodePreview` notices and calls `onEnd('stopped')`, so don't play through `audioEngine.play`
directly from a node.

## The desk

The desk is where material is set aside to be reused, and where it is authored. Everything else in the workbench derives its output from something; the desk holds data-blocks: copies the composer chose to keep (capture, Send to desk, duplicate, convert) or blank data-blocks started from nothing and edited directly in the editor of their type (below). A data-block can be placed back into a node tree as a source (Make source). Not built: any "Assign register" step that turns pitch classes back into playable notes, editors for data-block types other than Notes, a lineage viewer, and a timeline or arranger.

### Data-blocks and their types

A data-block is the registry's stored envelope (`dataBlocks/registry.ts`; `dataBlock.ts` holds the packet-block functions):

```ts
interface PacketBlock {
  schemaVersion: 2;
  id: string;
  typeId: string;               // the registered type, stored (never inferred from the packet)
  name: string;
  note?: string;
  createdAt: string;
  payload: { kind: 'packet'; packet: DataPacket };  // the head packet, any kind and domain
  origin?: { nodeInstance: string; portId?: string; itemIds?: string[] };  // itemIds absent = whole packet
  lineage?: DataBlockLineage;    // see Edit contract and versions
}
```

The packet already carries its own kind, domain, role and frame, so routing compatibility works on a data-block unchanged and nothing about the desk is specific to notes. `origin` records where a capture came from and is information only: nothing follows it afterwards, and capture is a copy. Items keep their original ids, and each gains a `capture` provenance step. The desk holds packet blocks only until the Collection record type (R4). **Baseline reset (R1, W-60):** the envelope `schemaVersion` is 2 (1 was the earlier shape with the packet at the top level and no `typeId`); nothing migrates it. On load a stored block with `schemaVersion` 1 is dropped (the desk says so and the next save deletes the record), a saved project's earlier-shape desk opens empty, and a block that is a newer version, has an unregistered `typeId`, or fails `validateBlock` (its packet is not accepted by its type) leaves the whole stored desk untouched and locked, as a corrupt desk always did. `acceptsDataBlocks` is that check.

**Data-block types (`dataBlocks/types/`, registry in `dataBlocks/registry.ts`).** The only place a data-block type is described; see "Data-block registry". Registered, with non-overlapping `accepts` (`dataBlocks/types/types.test.ts` proves every sample packet is accepted by exactly one): Notes (`notes`: `events | note`; editor `note-roll`, operators, audition through the note performance plan, refusing when empty), Pitch set (`pitch-set`: `list | pitch`), Pitch classes (`pitch-classes`: `list` or `events` with domain `pitchClass`; the desk's To pitch classes makes the events form), Rhythm (`rhythm`: `list | duration` or domain `rhythmPattern`), Values (`values`: `list` or `value` of `integer` or `rational`). Only Notes has an audition; the others report "<Label> has no audition yet." (Values: "Values have no sound of their own.") until R2/R3. `dataBlockTypes.ts` keeps only what is not registry: `registerDataBlockEditor` and `dataBlockEditorOf` (the component bound to a type's `editorId`), `operatorsOf`/`operatorById`, `barsLength`, `nextDataBlockName`, and the import that registers the built-in types. The New data-block control offers the types that have an editor (Notes today). A packet no registered type accepts cannot be sent to the desk (capture refuses with a reason).

**Frame and extent as data-block length.** For a plain notes data-block the packet frame's extent (`frame.extent` and `musicalExtent`, quarter notes) is the data-block's total length, which the editor shows as the end marker. Notes may run past it and are kept, never clamped. Other frames (cyclic, pulse, abstract: rhythm outputs, Interference and Fractioning results, pitch classes, Melodicization's cyclic notes) keep the frame contract that extent is the sum of durations, which a quarter-note total length would break, so notes properties do not apply to them.

**Notes properties (`metadata.notes`, `notesProperties.ts`).** A notes data-block also has a playback start, a loop (on or off, start, end) and a time signature. Total length is the frame extent; the other four live in `packet.metadata.notes` (`start`, `loopOn`, `loopStart`, `loopEnd` as exact rationals, `timeSignature` as `n/d`). `readNotesProperties` reads them; `withNotesProperties` writes them and keeps unknown keys already in `metadata.notes`. Positions are shown and typed as bars.beats.ticks (960 ticks per quarter, `meterTime.ts`; the meter decides bar and beat length). The inspector's `NotesPropertiesPanel` edits them as ordinary versioned, undoable edits (operation `edit-properties`); invalid input is rejected with a message, never clamped, and a value equal to the current one writes nothing. The loop is edited as an on/off "Looping" button plus Start and an absolute Length (loop end = start + length; a Start edit that would pass the data-block end shortens the Length).

- **Defaults on read, freeze at first edit.** A data-block without `metadata.notes` reads as 4/4, start 1.1.0, loop on over the whole length; reading never writes. Its length is the stored frame length exactly; if its content runs past that, or it has no frame, the length is the content rounded up to a whole bar of its meter (at least 4 quarters). The first edit of any kind to such a data-block writes the whole default set (`freezeNotesProperties`, length from the content at that moment) in the same packet, version and undo step as the edit, so the length never drifts as notes move and undo restores the old packet exactly. Once a data-block carries `metadata.notes`, its frame length is the composer's, kept even under the content. A malformed stored field falls back to its own default.
- **Applicability.** Only `events | note` with linear (or no) topology and a `quarterNote` (or no) frame (`notesPropertiesRefusal`). For other data-blocks the panel is not rendered and `editNotesProperties` / `withNotesProperties` refuse and never write.
- **Cap.** `MAX_DATA_BLOCK_BARS` is 72000 bars; longer typed lengths are rejected, and an older data-block already longer reads as exactly the cap (notes past it are kept).

The desk is a list of data-blocks, provided by `DeskProvider` at the workbench root so every node sends to, and every view reads from, the same list. Its storage is IndexedDB, not the workbench's localStorage (see History, storage and projects).

### Capture

Capture takes a packet and, optionally, a set of item ids. Without ids it captures the whole packet, which works for any kind. With ids it needs a handler for that kind in `captureHandlers` (`dataBlock.ts`), which selects the items and makes the result self-contained. A kind with no handler is refused with an explanation, never guessed at. Today only `events | note` has one: it keeps the selected notes in packet order, shifts them so the earliest starts at zero (exact rational time), makes the frame linear with origin 0 and drops the source grouping with a warning, because its boundaries are positions in the source. Pitch is stored absolutely.

To support a new kind (a drawn curve, a painted gesture):

1. Add a handler to `captureHandlers` for partial capture, if selecting part of it means something. It must return a self-contained packet: positions rebased, a frame that describes the part, no references into the source.
2. Add a preview branch to `DataBlockPreview`, which chooses a renderer from the packet's signal category (`signalCategories.ts`) and falls back to the values as text.
3. Add audition in `DeskView` if the kind can be played; the card disables the button otherwise.
4. Keep the packet JSON-safe (plain numbers, strings and arrays), since the desk is serialised as is, and bump `schemaVersion` if the stored shape changes.

The desk, persistence and the source node need no change.

### Desk view and audition

The desk is the `desk` panel of the Stage, in front in the **Desk** workspace (and in any workspace the person puts it in), switched with the status bar's workspace tabs. It is `keepMounted`, so it stays alive in the other workspaces, parked and `inert`, never `display: none`: the canvas measures its own box, so collapsing it made it refit to a tiny view, and its elements set `visibility: visible` themselves, so `visibility` alone let its nodes show through the desk (the Stage's parking applies all three).

Cards preview a data-block, rename it, edit its note (`editDataBlockNote`; blank text clears it), duplicate it, convert it to pitch classes, delete it (two clicks) and audition it. Audition runs on the transport (`followTransport`), so the metronome and count-in apply as for any node preview. A selection auditioned from a roll plays rebased to zero, so the roll's playhead starts at where the selection sits in the data-block and covers its length. Audition is disabled for anything but `events | note`, so a pitch-class data-block cannot be auditioned: pitch classes have no register.

### Variations and pitch classes

**Duplicate as variation** (`duplicateDataBlock`) adds a copy named `<name> (variation)` directly after the original, with a fresh id, a deep-copied packet, and the note and `origin` copied. Items keep their ids and each gains a `duplicate` provenance step. The original is untouched, and the two share no state.

**Convert to pitch classes** (`convertDataBlockToPitchClass`) adds a copy named `<name> (pitch classes)` after the original. Only a non-empty `events | note` data-block with finite pitches converts; anything else is a hard refusal with an explanation. Each pitch becomes `round(midicents / (1200 / edo))` mod `edo`, where `edo` is the project EDO, and the packet's encoding becomes `chromatic-<edo>`. The result is `events | pitchClass` with items `{ onset, interOnset, duration, pitchClasses, velocity }`: timing and frame are kept and the register is dropped. A pitch within `PITCH_GRID_TOLERANCE_MIDICENTS` of an EDO step is on the grid and converts directly. If any pitch is off the grid the call returns `needsSnap` (with the count) and converts nothing; the desk then prompts Snap or Cancel, and only a call with `snap: true` rounds to the nearest step. Each item gains a `to-pitch-class` provenance step recording `edo` and `snappedCount`.

Routing accepts pitch-class events for any `chromatic-<edo>` through `signalTypes.ts` (the `matches` predicates of the signal type registry). Pitch List requires `kind === 'list'` upstream, so an events packet is no longer read as a list.

### Edit contract and versions

A data-block is edited by replacing its packet atomically on the same data-block id; the packet is never mutated in place. Make-source nodes read the data-block by id, so every edit, restore and undo updates their output and every receiver.

**The edit path.** There is one: `commitDataBlockEditById(id, packet, operation, { handEdit?, coalesceKey? })` on the desk context. It reads the desk's latest data-block (`latestDataBlockById`, not any render's copy, so an edit never reverts one that landed since), runs `commitDataBlockEdit`, and goes through `applyChange`, the workbench history's recorder. It returns `ok: false`, without touching any edit session, when the desk refused the change (loading, locked, frozen for a project open). Callers build every edit from `latestDataBlockById` at commit time; a value equal to the current one makes no version. `commitDataBlockEdit(dataBlock, newPacket, operation)` keeps `id`, `createdAt`, `name`, `note` and `origin`; it returns `{ ok: false, error }` and never throws for a packet that is not plain JSON (cyclic included), not valid, or that changes `kind`, `domain` or `encoding` (that is a new data-block with `derivedFrom`); a packet deeply equal to the current one changes nothing. Added and modified items gain a provenance step `{ transformation: operation, parameters: { dataBlockId, versionId, change } }`; unchanged items get none. Item-id stability is the caller's obligation (an editor must keep the id of a moved or changed item); nothing enforces it, so provenance and diffs by id are only as good as the editor.

**Operator names.** A note-editor gesture commits as `edit-notes`, a property edit as `edit-properties`, a transform as `transform-<action id>` (`transform-paste`, `transform-rotate-time`, ...); conversions and duplicates have their own names (`to-pitch-class`, `duplicate`). (`rhythmEdit.ts`'s `edit-length` / `edit-rhythm` are not desk edit operations: they are per-item provenance stamps that node writes on its own items.) The name is provenance only; it never decides whether an edit is a hand edit.

**Versions.** A data-block keeps a stored derivation tree of snapshots so any earlier state can be viewed and returned to:

```ts
interface DataBlockLineage { head: string; versions: DataBlockVersion[]; derivedFrom?: DataBlockDerivation }
interface DataBlockVersion { id: string; parentId: string | null; at: string; operation: string; packet?: DataPacket }
interface DataBlockDerivation { dataBlockId: string; versionId: string | null; operation: string }
```

- The head is the data-block's current packet: `payload.packet` is the head's content and the head version stores no `packet`; every other version carries its snapshot. `acceptsDataBlocks` enforces this, plus one root (`parentId: null`), every `parentId` a kept version, no cycles, plain JSON.
- Never-edited data-blocks store no lineage. The first edit creates the root version (`original`, at `createdAt`) from the pre-edit packet, then a child that becomes the head.
- Derived data-blocks (Duplicate, Convert to pitch classes, Create from version) are born with a one-version lineage whose `derivedFrom` names the source data-block and its head version; `versionId: null` means the source's original state, which becomes its root if it is ever edited. A new data-block never copies the source's tree.
- `restoreDataBlockVersion` moves the head to a version (the version left keeps its snapshot; a later edit branches from the restored one). `createDataBlockFromVersion` makes `<name> (from earlier)` with `derivedFrom`.
- **Hand edits versus versions.** Versions mark meaningful moments: creation or capture (the root), a transform or conversion, a restore, and one version per hand-edit session. A hand edit is a commit with `{ handEdit: true }`; within a session every such edit amends the head version in place (the head keeps its id, its `at` advances, provenance is stamped once relative to the version before the session). A session continues while the operation is the same, the head is still the version it amends, and the previous edit was within `EDIT_SESSION_IDLE_MS` (3 minutes). It ends on `endEditSession(dataBlockId)` (the editor slot calls it when the target moves off the data-block), on a different operation, on idle time, and on a restore. An edit without `handEdit` (every transform, a property edit) always makes its own version. Session state is a transient map in `dataBlock.ts`, never stored.
- **One undo step per edit.** Undo is decoupled from versions: each undo step holds the whole data-block before and after, lineage included, so several steps can lie inside one version. `coalesceKey` (same key within 500 ms) merges steps of one gesture, for the history only. Every committed edit, transform and restore is one undo step.
- **Bounds.** Each lineage is capped at `MAX_DATA_BLOCK_VERSIONS` (500) and `MAX_LINEAGE_CHARS` (20M JSON characters including the head packet). `pruneLineage` runs on every edit: the root and head are never dropped, the oldest interior version goes first, then the oldest branch tip, and children are re-parented so the tree stays connected. Pruning discards snapshots for good.

Lineage can show every kept packet exactly, the branch structure, when and by which operator each version was made, and which data-block it came from. It cannot show pruned versions, edits from before a data-block had a lineage, or the exact derived-from state of a source that was never edited and then changed.

### History, storage and projects

**Session history (`history.ts`).** One workbench-wide undo/redo, bounded (`HISTORY_DEPTH` 50) and session-only: nothing about it is stored. `usePersistentState` records each write as `(key, previousRaw, nextRaw)` and keeps a registry of appliers (registered by the state store per key, mounted or not) so undo writes through the store; node add/remove, canvas moves and connections, the desk and the settings go through the same recorder. Writes within 500 ms with the same key or in the same tick coalesce (closed by pointerup, pointercancel, focusout). Transient keys (`unrecordedStateKeys`: playback, hover, selection, view, scroll) record nothing, and auto-resets fold into the step that triggered them. The shortcut (Ctrl/Cmd+Z, Shift+Z, Ctrl+Y) works everywhere, text boxes included, and the top bar has Undo and Redo buttons. Every persisted `compositionSettings` field is one virtual key `${STORAGE_KEY}#settings` (whole JSON), so settings undo exactly and mark the project unsaved. The desk records only the data-blocks that changed (`previousValue`/`nextValue` on a virtual `HistoryChange`, sharing live data-block objects) and the order, not whole-desk strings. `historyChangeCount()` counts every change (and undo/redo); the project menu compares it with the count at the last save or open to know the workbench is dirty.

**Desk storage (`deskStore.ts`).** The desk, lineage included, lives in IndexedDB (database `hrifa-workbench`): one record per data-block in `desk-data-blocks` plus an `order` record and a `rev` counter in `desk-meta`, so a write touches only changed data-blocks (by reference) and the order, in one transaction. Records are v1 `DataBlock`s validated with `acceptsDataBlocks` on load. All reads and writes go through one queue (`enqueueDeskTask`). `DeskProvider` starts `loading`, loads once, refuses changes until then, and loading never writes. Writes are debounced (150 ms; 1000 ms while edits are coalescing), serialised and flushed on unmount and `pagehide`. **Two tabs:** each tab remembers the `rev` it last read or wrote; a write whose transaction finds a different `rev` aborts and sets `persistError` ("The desk changed in another tab. Reload to see the latest version."). Load is tolerant (an order id with no record is skipped, a record the order lacks is appended, with a warning); unreadable or newer data is left untouched and the desk reports `locked`: changes are refused and nothing is written over it. A failed write sets `persistError` (shown as a warning on the desk), cleared by the next success. `navigator.storage.persist()` is requested once, best effort.

**Projects (`projects.ts`, `deskStore.ts`, `components/ProjectMenu.tsx`).** A project is every raw workbench localStorage key plus the whole desk with lineage, stored in IndexedDB (database `hrifa-workbench`, version 1: `projects` holds name, time and raw keys, `project-desks` the desk, so listing never reads desks). Opening replaces everything and then reloads, with no merging: `openProject` refuses while the desk is loading or (for a project with a desk) locked, sets the module-level reloading flag (`reloading.ts`), writes the desk through `replaceDesk(desk, { reloading: true })` (one transaction with the `rev` check), then the localStorage keys; on failure the keys and previous desk are put back (`{ restore: true }`) and the flag cleared. While the flag is set the dying page writes and records nothing (`usePersistentState`, settings and history skip storage, `recordChange` is a no-op), so auto-resets cannot dirty the project or overwrite restored keys. Any failure changes nothing on screen or in storage and shows the reason. A project saved while the desk was unreadable has no desk and leaves the desk alone on open. The current project (id, name, dirty) is kept in `hrifa.workbench-current-project.v1`, outside the workbench prefix; opening while dirty asks Save first / Discard / Cancel. Export/import files carry the desk and lineage. The top-bar `DeveloperMenu` holds per-viewer options (`developerOptions.ts`, `hrifa.developer-options.v1`, outside projects and history); "Open transport and sounds too" decides whether opening a project replaces settings.

### Make source

Make source places a data-block on the canvas as a `data-block-source` node (`DataBlockSourceNode`). The instance carries a `dataBlockId` and publishes the data-block's packet unchanged on one output, so any node that accepts that kind of packet can read it; a note data-block can feed the Mixer. The desk owns the material and the node keeps no state of its own. If the data-block is deleted the node publishes nothing and receivers show a missing source. It is not in the Add node menu, so a desk item never lands on the canvas unless the composer asks, and it is disabled for an empty data-block.

### References and users

`dataBlocks/dataBlockRefs.ts` (pure, node env, no storage or React; W-57) (built-in `data-block` referencer, W-59: a registered record type's `refs(data)` entries, each under a stable `slot`, are users with no hand-written referencer; a `UserEntry` carries `slot`, and unlink, make single user and remap match on kind, owner and slot; `registerReferencer` throws on a duplicate name; `missingRefs` lists references to blocks no longer on the desk) computes who uses a data-block. A reference is `{ id, version? }`; a **referencer** is registered with `registerReferencer({ name, refs(project), repoint(project, entry, toId | null), accepts? })`, and `dataBlockUsers(project, id)` / `dataBlockUserCount` walk the registry over `RefsProject { dataBlocks, instances, extra? }`. Users are never stored and never listed by hand. The only real referencer today is the Make source node (`nodeReferencer`: `dataBlockId` on a `data-block-source` instance, label "<instance label> (node)"); a collection, a timeline strip or a modifier input is one more registration (tests register fake ones).

Not users: `origin`, `lineage.derivedFrom`, the editor target, the inspector target, pins. Deleting a data-block breaks none of them. `dataBlockDescendants` (by `derivedFrom`, transitive) names what loses its source; `deleteImpact` returns `{ users, descendants }` for the delete confirm. Delete does not cascade: users show "missing".

The operations are pure and return the next project; nothing in the module records history. The caller applies the result through the recorders that exist: the new `dataBlocks` through the desk's `applyChange`, the new `instances` through the instances' persistent state, both inside one `recordGroup` so one operation is one undo step. `makeSingleUser` (copy "<name> (variation)" derived from the original, placed after it, repoints one user), `unlinkUser` (a Make source with no `dataBlockId` is its blank state and renders as a missing data-block), `remapPreview` then `remapUsers` (refused where a referencer's `accepts` refuses; today only a Make source refusing an empty data-block via `makeSourceRefusal`), `unusedDataBlocks`, `purgePlan` and `purge` (nothing is dropped automatically). No UI uses them yet (B2: user counts, the "Used by" list in the delete confirm, Unused filter, Purge).

## Direction: rolling playback and arrangement

The end goal for playback is a **rolling scheduler**, and the arrangement view is what will need it. Today a `PerformancePlan` is a finished, finite list of events that the engine schedules up front. That suits a short plan (a mixer pass, a single node's preview), but a timeline arrangement needs the engine to ask for events as time advances: edit while playing, jump to a position, loop a region, change tempo, and open a large project without building every event first. DAWs work this way, scheduling a short lookahead window ahead of the audio clock.

The mixer's long-period case is the same problem. A DAW-style launcher never computes the least common multiple of its items' lengths: each item keeps its own loop and its next repeat is scheduled as it comes up, so the realignment simply happens. The mixer's `free` loops already have those semantics; unrolling one realignment pass is a workaround for not having a rolling scheduler.

The shape this implies:

- **A window function.** Compiling a mix, and later an arrangement, answers "which events fall in time A to B?" instead of "give me the whole plan". Today's finite plan is the special case A = 0, B = pass length. Free and restart-with-longest loops are cheap to window; arrangement data-blocks are windowed by their position.
- **A scheduler in the engine.** A timer wakes ahead of the audio clock, asks the window function for the next bars, and schedules them on the transport. Events land on their own ticks, so the whole-tick rounding of a looped pass goes away. The scheduler must tolerate a late timer without dropping notes.
- **Live edits, seek and loop regions** become rules about when a changed source takes effect and from where the window restarts. Today's rule, that edits apply on the next Play, is a simplification the scheduler replaces.
- **The roll becomes a view onto a window**, not a full draw of one pass.

Stopgaps to treat as stopgaps, working and tested but not to be deepened: `PlaybackRequest.loop` and its transport loop points, the mixer's horizon and truncated pass, and the whole-pass unrolling in `compileMixerPlan`. The window function and scheduler should replace them, with the loop path kept only where a short seamless pass is genuinely simpler.

An arrangement also needs what streaming alone does not give: a timeline model (data-blocks, positions, tracks, a tempo and meter map), editing, and committed multi-stream packets. What a committed multi-stream packet is (the `layers` kind) is deliberately undecided; see the Mixer section, which publishes none.

## Data-block registry (rebuild, R0 and R1)

`dataBlocks/` holds the ground-up registry (W-58, W-59). R1 (W-60) registered the real packet types in `dataBlocks/types/` and moved the desk, Make source and capture onto it; the old `dataBlockTypes.ts` registry and the `DataBlock` type are gone.

- Envelope (`registry.ts`): `{ schemaVersion, id, typeId, name, note?, createdAt, origin?, lineage?, payload }`, `payload` one of `{ kind: 'packet', packet }` or `{ kind: 'record', data }`. The type is stored; records have no version tree.
- `registerDataBlockType(def)` (a duplicate id throws), `dataBlockTypes()`, `getDataBlockType(id)`, `dataBlockTypeOf(block)` (by stored `typeId`), `dataBlockTypesByFamily(family)` (browsing only), `chooseTypeId(packet)` (capture time: the first matching non-generic type, else the first matching generic one; the stored `typeId` is never re-guessed), `validateBlock`, `duplicateBlock`, `isBlockEmpty`, `auditionSupport(def)`, `auditionRefusal(block)`. A def: `{ id, label, family, channels, payload, createBlank, preview?, editorId?, audition?, noAuditionReason?, duplicate?, isEmpty? }`, plus `accepts(packet)` on packet types (choose and validate only) and `validate`, `refs`, `mapRefs` on record types. No React: `preview` is an id or `{ id, options }`.
- `acceptance.ts`: `registerConversion({ id, from, to, label, describe, convert })` per type pair; an `InputSpec` is `{ accepts, conversions? }`; `typesAccepting`, `reinterpretOptions`, `pickerFor` (exact, then reinterpret) and `applyConversion`. Nothing converts unless one is chosen and applied.
- `dataBlockRefs.ts` (moved here): see "References and users" in "The desk".
- `types/`: the built-in packet types (R1), one small file each plus `blank.ts` (blank packet helpers, `refuseWhenEmpty`) and `index.ts` (registers them once when first imported). A def may also carry `operators` (the inspector's edit actions). `isPacketBlock`, `makeSourceRefusal` and `DATA_BLOCK_SCHEMA_VERSION` live in `registry.ts`.
- Types and families (W-61): a type is a kind of thing a composer keeps, edits and hears as a unit; meaning stays a tag on the data (`domain`), not a type per meaning. `family` (`pitch`, `time`, `placed`, `composite`, `generic`) is for browsing and filtering and never decides a stored type; `channels` lists what the type holds (`onset`, `duration`, `pitch`, `amplitude`, `timbre`; may be empty). Registered: `notes` (placed; onset, duration, pitch, amplitude), `pitch-set` and `pitch-classes` (pitch; pitch), `rhythm` (time; onset), `values` (generic), and the generic `list` and `bank` (kind `list` or `bank` of ANY domain; no editor, no audition, so the New control does not offer them). No two non-generic types accept the same packet; generic types may overlap them; every `list` or `bank` is accepted by some type. Still held by no type: `tree`, `layers`, `curve`, `value` of other domains, `events` of other domains.
- `testTypes.ts`: test-only types (pitch-set-like, rhythm-like, notes-like, collection record).

## Rules for extending the vocabulary

- Add a kind only when the structure is genuinely different, not because a new node produced it.
- Add or refine a domain when substituting another domain would change musical meaning or validation.
- Keep topology, extent, unit, origin, and grouping in the frame rather than encoding them into a nominal type name.
- Make conversions explicit and inspectable. Do not silently reinterpret, clamp, or discard values.
- Preserve source item identity and provenance through direct operations.
- When streams must align, expose the alignment policy (`zip`, `cycle`, `cartesian`, or another named rule).
- Keep rejected parameter frames and reasons available instead of silently dropping invalid combinations.

## The Notes editor

### The editor slot

The bottom panel of the workbench frame shows an **editor target**: a node instance or a data-block, never both. Double-clicking a desk card (or creating a data-block) targets that data-block and expands a collapsed panel. `DataBlockEditorSlot` looks the editor up through the data-block-type registry (`dataBlockEditorFor`: type, `editorId`, `registerDataBlockEditor`); a data-block type with no editor shows a plain "No editor for this data-block yet" state. While a data-block is open no node counts as active (inspector setup controls, Play selected, canvas highlight), and the left inspector shows the data-block's properties and actions instead of a node. What is open stays open: deleting another node or clicking empty canvas leaves the panel alone, and if the open data-block vanishes (delete, undo, project open) or the open node is removed, the panel goes blank; nothing else is promoted into it. The slot ends the data-block's hand-edit session whenever the target moves off the data-block. Node views stay mounted and hidden when not shown (to keep their playing preview, selection and scroll; their evaluation and publishing belong to the runners), as in the frame section above. The target is shown by the `node-detail` and `data-block-editor` panels of the `Detail` docker; clicking the other tab shows its blank state and does not change the target.

`NotesEditor` (`components/NotesEditor.tsx`, editor `note-roll`) owns no data-block state beyond the packet: it reads the data-block, applies edits through the edit contract and reuses the `EditorPalette` chrome. Everything below is state that lives in the editor, never in the packet, history or a project.

### Edits from the editor

`NotesEditor.commit` is the choke point for note edits. It reads the desk's current packet (`latestDataBlockById`), freezes an old data-block's properties (`freezeNotesProperties`), builds the edit on that, resolves same-pitch overlaps for the notes the edit touched, and commits through `commitDataBlockEditById` as `edit-notes` with `handEdit: true`. An edit that changes nothing writes nothing (not even the freeze), and one whose additions are all absorbed by existing notes (an identical note) writes nothing. Each gesture (draw, move, resize from either edge, delete, velocity drag, paint, knife, eraser, time move) is one commit, one undo step, and part of one version per edit session. The editor's `PianoRoll` (`src/components/PianoRoll/`) is prop-driven and opt-in: it reports edits through callbacks (`onResizeNotes`, `onResizeNotesStart`, `onPaintNotes`, `onSplitNote`, ...) and Melodicization and Mixer, which pass none, keep their behaviour. Transforms and notes properties do not go through `commit()`: transforms use `runOperator` and properties the panel, each freezing and committing on its own through the same desk path.

**Same-pitch overlap rule** (replaces the old "merge duplicates to the longest duration"). `resolveSamePitchOverlaps(packet, base?, newId?, lineage?)` (`notesEdits.ts`) returns `{ packet, survivorOf, created, removed }`. Both commit paths (`NotesEditor.commit` and `runOperator`) pass the pre-edit packet as `base`; a note is TOUCHED when it is new (id not in `base`) or its onset, pitches or duration differ (velocity and label never count, so velocity edits can never trigger the rule; no `base`: every note is touched and no pair is pre-existing). Only NEW overlaps are resolved: a pair is PRE-EXISTING, and left exactly as it was, when both notes are base notes or pieces of base notes (a rotation's wrap pieces `<id>~r1` too: `runOperator` builds `lineage` from `rotation.pieceIds` and compares against the session's ORIGINAL notes, so an old overlapping pair stays untouched across every press of a rotation session; `lineage` also maps the fresh id of a knife half or time-move piece to the base note it was cut from: `splitNote` right half, `timeMoveResult.pieceOf`) whose base spans overlapped at the same single pitch. So velocity edits, nudges and resizes of one note of an old pair, moving an old pair together, knife cuts and time-selection cuts never cut an old partner, and an old identical pair stays two notes; a new note, a copy, a note moved or transposed onto a note it did not overlap in the base, or a piece landing on an unrelated note still resolves. Only single-pitch events take part; chords (multi-pitch items) neither overwrite nor are overwritten. The notes of an old overlapping pair are not unified by later edits: that is by design (clean-up of old data-blocks is the user's, not a side effect). Time-selection moves in Alt (merge) mode still overwrite same-pitch notes at the destination through this rule (a pitch never has duplicates or overlaps, as in Bitwig), and transforms and keyboard moves overwrite same-pitch neighbours they land on in clean data-blocks. Edge-sharing is not an overlap. A touched note T and another same-pitch note O:
- identical onset AND duration: they merge. O (the existing/untouched one, or the earlier touched one) keeps its id and position and takes T's velocity, T is dropped (`survivorOf` T -> O);
- otherwise T OVERWRITES the span it overlaps on O, exactly in rationals: the part before T keeps O's id, the part after becomes a NEW piece (id from the `newId` the caller passes, collision-safe; value, velocity and provenance copied like the knife; label recomputed; slot = length; placed right after O), O fully covered is removed (`removed`), and O overlapped on one side is just shortened and keeps its id. Whole note + quarter dropped on beat 2 = q (original id), q (dragged), h (new piece); a quarter at the whole note's onset = new q + O shortened to the remainder (same id);
- two touched notes that overlap: the one with the LATER ONSET wins (a tie: the later in packet order), whatever the packet order. The touched notes act from the weakest to the strongest (ascending win order), each against the live pieces including the fresh halves its losers left, so nested touched notes (C 0-5, B 1-4, A 2-3) give the same final spans for every packet order and never leave a same-pitch overlap behind. Overlap candidates come from one sweep per pitch (cuts only shrink spans), not from a scan of every note per touched note. So Ctrl+Right on a whole selected legato run of one pitch gives the same result for any packet order: each note grows by a unit, then each later note overwrites the overlap of the earlier one, so only the last note keeps its extra unit (a 0-1, b 1-2, c 2-4 from a 0-1, b 1-2, c 2-3).
It runs inside the same version and undo step and returns the same packet by reference when nothing changes. Selection after: a touched note stays selected, merged-away ids map to their survivor (`mapMergedIds`), covered/removed ids drop out, created pieces are NOT added; the rotation session ends whenever the rule changed the packet. A result identical to the base items (additions absorbed by an identical note) writes nothing.

### Keyboard note editing

In the editor's focus scope (roll, lane, panel body; `onKeyDown` on the roll area, after children such as the lane splitter have had the key) the arrow keys act on the SELECTED notes, one hand-edit commit (one undo step, so the overlap rule applies) per press. Auto-repeat is allowed for all of them: the editor keeps the latest selection in a ref written synchronously by commit, adopt and navigation, so presses landing before a re-render never read a stale selection (a move right after a merge acts on the surviving note). Off-grid notes move and resize by exactly one grid unit and are not rounded to the grid. Pure parts are in `noteKeyboard.ts`: Left/Right move by the editor's snap unit (clamped so the group stops at 0); Up/Down by 100 midicents (one semitone: the roll's rows are the 128 MIDI semitones and ignore the `edo` setting, which only colours notes) and Shift+Up/Down by 1200 (12 rows), refused as a whole group when any note would leave 0-12700; Shift+Left/Right nudge by the effective snap unit divided by `NUDGE_GRID_DIVISOR` = 8 (three subdivisions finer: grid 1/1 nudges 1/8, 1/4 nudges 1/32; triplets and Auto follow the snap unit; exact rationals via `rationalFromNumber`), never finer than `MIN_NUDGE_QUARTERS` = 1/1024 of a quarter (`nudgeQuarters(unit)`; when the floor binds the key still nudges by the floor); Ctrl/Cmd+Left/Right lengthen/shorten by one snap unit, each note held on its own (a note at or below one unit is not shortened, never below it, the others still change); Alt+Left/Right navigate: notes ordered by onset ascending then pitch high to low (a chord event by its top pitch, then packet order), Right with several selected picks the first of them alone, with one the next, with none the first note (Left mirrors; stays at the ends), a visually hidden `aria-live="polite"` status announces the note (for example `G4 at bar 1 beat 1, selected, 1 of 4`, bar and beat from the data-block's time signature, position in the navigation order), and the roll scrolls the note into view (`PianoRoll` `reveal={ id, token }`, opt-in, nearest-edge scroll; a `{ start, end, pitchMidicents, pitchEndMidicents?, token }` span variant reveals a time and pitch range the same way). Ignored in text fields, during a pitch pick, while any pointer button is down (a window-level tracker covers every drag and lane gesture; a lost release is recovered by any pointermove with no button down, for mouse, pen and touch, and by pointerup, pointercancel, lostpointercapture and blur) and when a child already took the key; a time selection takes the keys and does nothing. Handled keys are `preventDefault`ed (so no scroll, no browser Back on Alt+Left; during a pick or gesture Alt+Left/Right is still swallowed), and the Alt keyup after an Alt+arrow is cancelled so the menu bar is not activated. Other modifier combinations are left alone, and none collides with tool numbers, V, Ctrl/Cmd+C/V, Delete or [ ].

### Unified roll and velocity panel

The roll, the velocity lane, the ruler, one horizontal scrollbar and the tool palette are one panel, one focus scope (`PianoRoll` with `detachedScroll`; the lane is a `lane` slot, `VelocityLane`). Tool number keys, `V` (lane toggle) and the shortcuts work after a click anywhere in it and are ignored in text fields. The palette spans the panel's full height. The velocity lane has a resizable height (splitter) and shares the roll's tool state.

**Single-truth horizontal scroll.** `view.scrollLeft` (timeline pixels) is the only truth. The roll's native scroller is hidden and re-pinned from it, and one controlled `HorizontalScrollbar` reports only its own moves. Echoes of programmatic scroll writes are filtered by `scrollSync.ts`: only the last written value is remembered, genuine scrolls clear it, and a change of zoom or scrollbar ratio forgets it, so a genuine scroll that lands on a written value is never swallowed. Wheel zoom is anchored at the cursor (anchor and scroll clamped to the visible roll); Shift/Alt+wheel and horizontal deltaX scroll sideways, the wheel over the keys scrolls pitch, and Ctrl/Meta+wheel zooms time (Ctrl+Alt: pitch).

**Windowed layer over 4M px** (`timelineLayout.ts`). Browsers cap element width (about 33M px Chrome, 18M px Firefox) and a 72000-bar data-block is up to 55M px. A timeline over 4M px renders a content layer that starts at an origin (a multiple of 2M px at or below the scroll position) and is 2M px plus three view widths wide; notes, bands, markers, lines, ruler labels and lane stems are positioned relative to the origin and cut to the drawn range; pointer positions add the origin back (`rollPoint`, used by every gesture including double-click and the context menu). The scrollbar scales a range over 8M px (`barRatio`: logical scrollLeft = native * ratio). Timelines up to 4M px are laid out whole.

**Grid density** (`PianoRoll/gridDensity.ts`, pure). From the grid unit, the meter, zoom (pixels per quarter) and the window it decides which lines exist and which bar numbers print. Lines: the finest level keeping lines at least `MIN_LINE_GAP` (10 px) apart, in order: subdivision (the selected unit when finer than a beat and 10 px wide; with Auto, a 1/32, 1/16 or 1/8 that has 28 px), beat, bar, then every 2nd, 4th, 8th, 16th... bar. Bar numbers (`barLabelStep`) thin independently, 1, 2, 4, 8... bars, the fewest keeping a label (digits at the data-block's length, 8 px each, plus 16 px) from touching the next; numbers sit on bars 1 + k * step. The editor passes `gridSourceFor(meter, gridUnit)`, a function `(from, to, pixelsPerQuarter, extent) => lines`; roll, lane and ruler all draw what it returns, asked only for the window (the view plus one view each side), so line count is bounded by the screen, not the data-block. An array `gridLines` (Mixer, Melodicization) is never windowed or thinned.

**Zoom range.** The roll's default time zoom is 16 to 192 px per quarter; the note editor passes `timeZoomRange` `NOTE_EDITOR_TIME_ZOOM` (0.25 to 192) so the far bar levels are reachable by buttons, wheel and Fit.

### Selection model

A `NoteSelection` (`noteSelection.ts`) is `{ ids, range, kind? }`: the selected events and the time range, which can reach over empty space. `kind: 'time'` marks a time selection (Time tool, or a Pointer marquee that caught no notes): only then the roll and lane draw the time band, and a pure time selection has a range and no ids. The range is the span the user dragged (additive drags union only overlapping spans), not widened to the notes it caught; the notes of a time selection are every note overlapping the span, including one that only touches an edge. A note selection shows a faint neutral band over the span its notes occupy instead; only one of the two shows. The time band is cleared by the next press on the roll, ruler or lane (not the scrollbar, palette or splitter), except a press inside the band, which starts moving its contents. A time selection survives undo, redo, deletes and outside packet changes (kind and range kept, pruned to the data-block). Selection is transient editor state: never in the packet, history or storage. Reported ids are sources, not rectangles: selecting any pitch of a chord selects the whole event (`sourceId`; geometry in `PianoRoll/selection.ts`).

**Time-selection move.** Dragging inside the band moves the block in time (grid-snapped, vertical ignored, clamped at 0): the part of notes inside the span moves and the parts outside stay (`moveTimeRange`, exact rationals; the stay part keeps the id, moved parts get fresh ids). Default overwrites the destination (straddling notes cut at its edges), Alt merges, Ctrl/Cmd copies (also for ordinary note moves). Ghosts preview it, Escape cancels, it is one hand edit, and after it the selection is the moved pieces with the band at the destination.

### Editor-side transient state

- **Band undo records.** The editor keeps the last 50 `{ beforeItems, afterItems, before, after }` records of time moves so an undo or redo puts the band back where it was; a record is used only when the packet and band both match it.
- **Rotation sessions** (`rotationSession.ts`), below.
- **ActiveRamp** (velocity lane, Paint tool): press sets the start percentage, release the end; heads between are interpolated by time position and joined by a dashed line, and the ramp stays active as a secondary selection. A plain right-button drag (no Alt needed) curves it (exponent on the 0..1 position), re-applied from the original endpoints as one more undo step, never stacked. It is valid only while the Paint tool is active, the packet's items equal what the ramp committed and the selection ids are the same; any other edit, tool change or Escape ends it. While armed, the lane handles the right button on `window` in the capture phase (pointer capture is released with the button, and the browser's context menu fires on button release on Windows and on press on macOS and Linux, at whatever is then under the pointer), swallows the menu for the right-button gesture and once after (a self-removing listener, 1 s at most). With no active ramp a right-click shows the browser's menu as usual. A LEFT press anywhere in the lane in the Paint tool (on a pin too: pins only drag velocities under Pointer, Eraser and Knife) always starts a brand-new ramp: the lane calls `onRampStart` at that press and the editor drops the previous ramp at once (its dashed line and armed state), so the new ramp's heads come only from this gesture's x range and never from the old ramp or the selection; a drag that catches no heads leaves no ramp rather than reviving the old one. Escape ends a ramp only while the focus or pointer is in the editor, and Enter applies a waiting pitch pick's default only while the focus is in the editor or the actions panel (or on the page body), never from an unrelated top-bar control.
- **Pick mode** (`pick` state, per data-block, so switching data-blocks drops it): the two-part pitch gesture of Invert and Make all pitches equal (below).
- **Entry length and velocity**, grid, lane height, collapsed lane and the Actions panel's open sections are per-viewer preferences (below).

### Per-viewer preferences

`noteEditorPreferences.ts` stores `hrifa.note-editor.v1` (outside the workbench key prefix, so projects never capture it, and never in history or a packet): `entryLength` and `entryVelocity` (what the next entered note gets: a plain click uses them; a drag from the press point sets length, snapped, at least one grid unit, and velocity, each past a 4 px dead zone, and the last drag becomes the new remembered value), `grid` (Auto, 1/1..1/32 and triplets), `velocityLaneCollapsed`, `laneHeight` (clamped to the panel when rendered) and `actionSections`. The New data-block defaults (`hrifa.data-block-defaults.v1`), developer options and the notes clipboard are likewise per viewer and outside history and projects. The "Color notes by scale degree" setting is different: it is a persisted composition setting (`compositionSettings`, in projects and undoable); degree colors come from `scaleDegreeColor.ts` (a fixed interleaved hue table at 12-EDO, a generic rule otherwise) and velocity is shown by saturation only.

**Persisted additions of data-block storage** (everything else the editor holds is transient and never stored: tool, selection, ramp, pick, rotation session, view): the optional `DataBlock.lineage` (stored with the data-block); IndexedDB `desk-data-blocks` and `desk-meta` (the desk), `projects` and `project-desks` (saved projects); and the localStorage keys `hrifa.note-editor.v1`, `hrifa.data-block-defaults.v1`, `hrifa.developer-options.v1`, `hrifa.workbench-current-project.v1` and `hrifa.composition-workbench.ui.editor-target.v1` (the data-block the bottom panel shows).

### Operators (transforms)

A data-block type lists **operators** (`DataBlockType.operators`, `dataBlockOperators.ts`): `{ id, label, group, params, applies(packet), run(packet, context, params) -> { ok, packet, selection?, message?, clipboard?, rotation? } | { ok: false, error } }`. An action is a pure function of the packet, the editor's selection and grid (`context`) and typed params; it never touches the desk or the DOM. `operatorsOf(packet)` and `operatorById` look them up by the packet's type, so the inspector panel, the editor's keys and a later right-click menu share one implementation. Only Notes implements them (`noteTransforms.ts`: scale, reverse in time, reverse order, rotate values, rotate durations, rotate in time, legato, transpose, quantize, duplicate, invert, make all equal (duration, velocity, pitch), copy, paste), each an exported pure function with its own tests. A param of kind `pick-pitch` is a pitch row the user clicks in the editor; its value is midicents (`midi * 100`) and `optional` says that leaving it out is the default (inversion's axis).

**Targets.** The selected notes; with nothing selected, every note; with a time selection, the notes overlapping its span with positive length (a touching note is not a target). Actions do not cut notes, with three exceptions: duplicate and copy of a time selection take only the part inside, and rotate in time cuts at the span's edges (below). The span is the selection's range, or with nothing selected 0 to the data-block length. Grid-based actions (quantize, rotate in time) use the editor's effective snap unit (the chosen grid, or on Auto the roll's adaptive subdivision). Data-block length never changes: notes pushed past the end are kept.

**Chord slots.** Items sharing an onset are one slot and move together in reverse order, rotate values and rotate durations. Notes always stay single-pitch items (an existing multi-pitch item moves as a unit). A slot receiving the payload of a slot with the same item count is rebuilt note by note; with a different count it becomes one single-pitch item per incoming pitch (repeats dropped), each keeping the velocity of its source and all at the slot's longest duration: the first kept items keep their ids, extras are removed, missing ones are created (fresh collision-safe ids, the slot's onset and first item's provenance). Direction: slot i takes from slot i - amount.

**Selection after an action** is exactly the notes that now make up the target: kept ids plus created ids, minus removed ones. Actions that create or remove items return `selection`; the others keep ids and the editor's default applies; a time selection keeps its range. Ids created by duplicate, copy, paste and rotation are collision-safe (`newNoteItemId` has a per-process counter; `copyNotes` and `timeMoveResult` skip ids already in the packet). Refusals return a message and change nothing; an action that changes nothing returns the same packet and writes no version, not even the freeze.

**Inversion and make all equal.** Invert mirrors pitches around an axis (`2 * axis - pitch` in midicents; microtones survive; default axis is the midpoint of the lowest and highest target pitch; a result outside 0..12700 refuses). Make all equal has `equal-duration` (a plain number is quarters, `a/b` a note value; blank = the first target's), `equal-velocity` (1 to 100 percent; blank = the first target's) and `equal-pitch` (picked row, required; a chord item collapses to the pitch).

**Rotate in time** is bounded and circular: nothing lands outside the span. A note crossing a span edge is cut at it first; only the inside part rotates, the outside parts stay, and the inside part that would pass the span end is split there and wraps to the start. The first part keeps the id; other parts get derived ids (`<id>~r1`, stable across presses). A split leaving a piece under 1/32 quarter refuses; zero steps return the same packet.

**Rotation session** (`rotationSession.ts`; transient, never in the packet or history). The first press records the original uncut notes, span, grid step, cumulative shift and extra-part ids; while the packet's items equal what the last press committed and the selection key is the one it left, each further press re-applies the rotation from the originals with the new cumulative shift. A whole number of spans rebuilds each original exactly (outside parts re-merged), so rotating back restores the packet. A different span or grid, a vanished original, any other edit, a selection change, undo or redo ends it for good. The editor passes it as `context.rotation` through the channel and keeps the one `adopt` receives. Each press is its own version and one undo step.

**Copy and paste** (`noteClipboard.ts`). The clipboard is in memory, per viewer (on `globalThis`, outside history, projects and storage), crosses data-blocks and holds the notes relative to the selection start. Copy takes selected notes whole (with a time selection, every note overlapping the span, whole), nothing selected is a message; the action returns the same packet plus `clipboard`, which the runner stores. Paste (`transform-paste`) lands at the time selection's start, else the earliest selected note, else the data-block start, with fresh ids; the pasted notes become the selection and the data-block length never grows. Ctrl/Cmd+C and V work in the editor's focus scope except in text fields and while a pick waits.

**Two-part pitch pick.** Invert and Make all pitches equal start from the panel: it asks the editor (`channel.beginPick`) to enter pick mode with callbacks. The roll shows a banner, a highlighted row and key and a crosshair through its `pickPitch` prop, and owns the click: `beginMarquee` turns a primary press (note or key) into `onPick(midi)` before any draw, marquee or selection code, so the pick never changes the selection (row = `127 - floor(y / pixelsPerSemitone)` from the roll's rectangle, clamped 0..127). Escape (window listener) cancels, Enter applies the default (invert only); another tool, data-block, action or the panel's Cancel also cancels.

**Running an action** (`dataBlockOperatorRunner.ts`). One function for the panel buttons and the editor's keys: it reads the desk's packet (`latestDataBlockById`) and the channel's selection now, freezes an old data-block, runs `action.run` (the only guarded call: an exception is logged and reported as an internal error, nothing committed), stores a copy's clipboard, resolves same-pitch overlaps for touched notes (`resolveSamePitchOverlaps`), commits as `transform-<id>` (its own version, not a hand edit, one undo step), then calls `adopt` in its own guard. It returns `committed | unchanged | refused | failed` with a message. `DataBlockOperatorsPanel` (left inspector, beside `NotesPropertiesPanel`) only collects params and shows the outcome as an alert, cleared when the editor's selection changes. It groups controls into four collapsible sections (Time, Pitch, Values, Clipboard; several open at once, state in `actionSections`).

**Editor -> inspector channel** (`noteEditorChannel.ts`). The open editor publishes `{ selection, gridUnit, snapUnit, rotation, picking, beginPick, cancelPick, adopt }` to a module-level store keyed by data-block id (after any render that changed them) and withdraws it on unmount. The panel reads the store when a button is pressed (never a render's copy), never writes the selection, and afterwards calls `adopt(result, committedPacket)` so the editor sets the selection the action asked for or keeps its own. Panel buttons default-prevent `mousedown`, so the editor keeps focus. The channel and the clipboard live on `globalThis` so a hot-reloaded module shares them with an editor published by the old copy (state without newer fields is tolerated with optional calls).

### Roll interaction details

- Tools (palette and keys 1-6): Pointer, Time selection, Pencil, Paint can, Knife, Eraser. A tool changes what a press does; an action does something once to the selection. One list of each feeds the palette, the right-click menu and keys. The default tool on open is Pencil for an empty data-block, Pointer otherwise.
- Note edge zones are `min(6 px, width / 3)` each side (`noteZone`, same rule for press and hover cursor): left zone resizes the start with the end fixed (`resizeNotesStart`), right the length, the middle moves. Moves and resizes show a ghost, Escape cancels, release commits once.
- Cursors are opt-in (`toolCursors`, inline SVG data URIs in `toolCursors.ts`, `--cursor-<tool>` properties with stock fallbacks), driven by `data-zone`, `data-alt`, `data-copy-key`, `data-gesture` and `data-copying`; modifier keys are tracked by window listeners that exist only while hovered with the opt-in or during a time-band drag.
- A selected item is an outline in `--text` and the marquee shows what it would select (THEMING.md, "State grammar").
