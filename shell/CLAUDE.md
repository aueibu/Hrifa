# shell/ working notes

(The repo-root `CLAUDE.md` still applies. This file adds workflow rules for `shell/`.)

## Layout

- `ARCHITECTURE.md`: shell-level map (layers, shared components, shared contracts, who consumes what). Each page keeps its own `ARCHITECTURE.md`; where a rule says `shell/ARCHITECTURE.md` it means this shell-level one, never a page's.
- `UI-RULES.md`: the human's standing UI rules (smooth and no flicker, page fits the window, reuse the reference component, theme roles, plain words, thin slice then stop). Read it before ANY UI work, and tell builders to read it in the brief instead of restating rules.
- `DECISIONS.md`: cross-project decisions log.
- `BACKLOG.md`: shared backlog; each item is tagged with its workstream folder name (`[workbench]`, `[tunings]`, ...) or `[shared]`.
- `ARC.template.md`, `PROGRESS.template.md`: copy into `arcs/<name>/` to start an arc.
- `arcs/<name>/DIGEST.md`: one-page builder summary of an arc (see "Workflow cost rules").
- `arcs/LOCKS.md`: shared paths currently being edited by an active arc.
- `arcs/<name>/`: a workstream folder (e.g. `workbench`, `tunings`). It holds the active `ARC.md` and `PROGRESS.md` plus archived finished arcs as `ARC.<topic>.md` / `PROGRESS.<topic>.md`. Starting a new arc in a workstream first archives the previous one (rename its files to `<topic>`). A one-off arc such as `structure` is its own workstream folder. `arcs/workbench/` has no active arc (finished one-off arcs sit beside the workstream folders: `arcs/structure/` holds the finished multi-arc structure arc, and `arcs/workbench/` holds the finished clips and desk arcs); its archives are `ARC.desk.md`, `ARC.clips.md`, `PROGRESS.desk.md`, `PROGRESS.clips.md`.

## Multi-milestone tasks

Several arcs can run at the same time. When a task is driven by an arc (template: `ARC.template.md`):

1. A task names its arc folder (`arcs/<name>`). If it names none, the orchestrator asks the human. The orchestrator passes that path to every agent it launches. Read only that arc's `ARC.md` and `PROGRESS.md` as the work log, first, including after any compaction. Resume from that `PROGRESS.md`'s "Next action". If the named folder has no `ARC.md`, stop and report (agents do not fall back to another arc; the only default is `arcs/workbench`, and only when `arcs/workbench/ARC.md` exists and the prompt names no folder).
2. Delegate by role: `scout` to locate things, `builder` to implement one milestone, `reviewer` to check it. Models are fixed in `.claude/agents/*.md`; do not override them.
3. Never advance a milestone while the arc's `Check command` fails (the workbench arc: `corepack yarn check:workbench`).
4. Update the arc's `PROGRESS.md` after every milestone step, and (in the milestone-end step, before the commit, not a separate ceremony) refresh `DIGEST.md` if data shapes, contracts or active locks changed: overwrite, never append, delete replaced rules, hard cap 100 lines. Nothing in `ARC.md`/`PROGRESS.md` is written by builders, reviewers or scouts: the orchestrator does it.
   - At the end of every milestone the orchestrator commits with path-scoped `git add` and `git commit -- <paths>` (owned paths plus the shared paths the arc holds a lock on; never a bare `git commit`), and only then removes the lock rows (rule 13 below).
   - If the gate is red only because of files outside the arc's owned and locked paths, it is not yours to fix (rule 14 below).
5. Stop and ask at every milestone marked "Human checkpoint" and on any "Stop-and-ask" condition. Otherwise keep going without asking.
6. Checkpoint decisions: every human decision is written back into the arc's `ARC.md` by the orchestrator (a "Checkpoint decisions" bullet under the milestone) before building on it.
7. Behaviour first, for any creation behaviour (a new feature, control, key, playback rule, data or save rule, display rule: anything the human could judge by using it):
   - **Scenarios first.** Before building, write the human's concrete cases as a small table (their actual notes, steps or data; say which roots, references or modes a rule uses) and get it confirmed. The options in a choice must be shown with an example where they give DIFFERENT results. Tests come from the confirmed table, never from a case where the options coincide.
   - **Thin slice first** for anything the spec cannot settle (feel, sound, look, key layout): build the smallest version the human can try, then polish, test and review after the behaviour is agreed.
   - **Restate before reworking.** When the human says something is wrong, restate in one plain sentence what they expected and what they got, using their own example, and ask only if the repro is unclear. Never rework on a guess.
8. Builder continuity (human OK 2026-11-25, a trial): keep the same builder across steps and milestones of the same arc while its context allows, resuming it with a precise brief for the next step. Each resume gets its own budget (rule 7 below), so a single run can never run away. Start a fresh builder when the summed tokens of its runs reach about 200k (the orchestrator adds up the usage each run reports; it cannot see a running count), when the follow-up changes the design and not just a detail, or when the next step is an unrelated concern (for example a React panel after evaluator work). If the trial costs more than it saves, the human reverts to fresh-per-step.

## Workflow cost rules (human OK 2026-11-25; cause: the strip detour S0 to L0 cost about 72% of one session's builder tokens)

1. **Consumer check.** Before a milestone that changes a stored record (fields of a registry type, record, desk or scene shape), write and get confirmed a table `Panel or op | Reads | Shows or does` for every reader inside the page (Outliner, Properties, Arranger, evaluator, ops, desk, project save) and every importing page. It goes in the arc's `SCENARIOS.*.md` or the milestone in `ARC.md` (template: `ARC.template.md`, "Consumer check").
2. **Static mock first for structure.** Adding or splitting entity levels, or changing panel hierarchy, gets a static HTML wireframe shown to the human before any data work. Not required for pure math or evaluator milestones.
3. **Short builder reports.** At most about 300 words: changed paths, exact check command with pass/fail counts, criteria checklist, open decisions or blockers. Detail goes in file pointers.
4. **Smaller builders.** A schema-changing milestone is split into (a) types, validation and migration and (b) evaluator, ops and scenario tests; each is one builder run capped at about 150k tokens (rule 8 above). A builder that is handed both does (a) only and reports.
5. **One verification side.** The builder runs `corepack yarn check:fast <changed files>` and `corepack yarn typecheck` once. The orchestrator does NOT re-run each file 3 times; it reads the builder's report, spot-checks one claim if it doubts it, and runs the arc's scoped gate once per milestone before the commit. Re-running a specific file several times is only for suspected flakiness (a flaky test is a defect: fix it, for example `waitFor` on settled state).
6. **Arc digest.** An arc with several milestones keeps `arcs/<name>/DIGEST.md` (about 80 to 120 lines: current contracts, owned and shared paths, active constraints, pointers). Builders read the digest plus the active milestone section of `ARC.md` instead of `DECISIONS.md`, `ARCHITECTURE.md` and the whole `ARC.md`; `UI-RULES.md` only for UI milestones. The digest has four short blocks (current contracts and shapes with file pointers, boundaries, key file map, UI-only pointer), is overwritten never appended, and is capped at 100 lines; the orchestrator refreshes it in the milestone-end step (rule 4) and prunes superseded milestone sections from `ARC.md` and stale "Next action" blocks from `PROGRESS.md` (keep exactly one "Next action"; git history keeps the rest). The workbench arc has one.
7. **Hard budget in every builder brief (human, 2026-11-25, angry after a U2 builder ran past 100k tokens with no cap).** The orchestrator writes into the brief: the budget (look-only port of ONE component: 60k tokens and 30 tool calls; any other single concern: 100k and 50 tool calls; never more than 150k), and "at the budget, stop and report what is done and what remains, even if unfinished". A builder that is told no budget uses the smaller one.
8. **One concern per run.** A brief covers one component, one panel or one pure module, never two (U2 was two panels: it should have been two runs). Look-only milestones are done by the orchestrator directly when they touch one file.
9. **Name the files, do not send the builder exploring.** The brief lists the exact files and line ranges to copy from ("reuse `Section` in `src/components/InspectorKit/Kit.tsx:121`, usage at `KitDemo.tsx:40-80`"), the files it may edit, and nothing like "read X and Y for reference". The builder reads only those plus `DIGEST.md` and its milestone section; for UI only `UI-RULES.md` sections 1, 3 and 6 plus any the brief names. If the brief cannot name the files, the orchestrator finds them first (one grep), not the builder.
10. **Cost questions get facts.** When the human asks about cost or tokens, the orchestrator says what it knows in two sentences (what was launched, with which budget; it cannot see a running builder's count) and offers to stop it. No lists of guesses, no menus. If a builder was launched without the budget in rule 7, the orchestrator says so and stops it unless the human says to continue.
11. A proposed eleventh item, one reviewer pass per group of look milestones, is NOT adopted yet (`BACKLOG.md`, "Workflow cost proposals").

## Several arcs at once

1. Task names its arc folder (`arcs/<name>`); see rule 1 above. Agents read only that arc's `ARC.md`/`PROGRESS.md` as the work log.
2. Every `ARC.md` declares `Owned paths` (the page folder, its tests, its own `ARCHITECTURE.md`, anything new it creates), `Shared paths it may touch` (see rule 10) and its scoped `Check command` (a `check:<arc>` script in `package.json`; the workbench keeps `check:workbench`).
3. An arc never edits another arc's owned paths. A page folder with no active arc (e.g. `src/pages/composition-workbench/` today) is a shared path: before another arc edits it, it takes a lock, adds a `DECISIONS.md` row and gets the human's OK.
4. Before editing a shared path an arc takes a row in `arcs/LOCKS.md` (path, arc, since, reason) and removes it only AFTER that path has been committed (rule 13). If the path is locked by another arc, wait or ask the human. Before committing a change to shared components or the theme, also run the consuming arcs' check (see "Who consumes what" in `ARCHITECTURE.md`, e.g. `check:workbench`).
5. Every arc starts with a context scan milestone (C0): read `shell/ARCHITECTURE.md`, `DECISIONS.md`, `BACKLOG.md`, the Status of every other arc under `arcs/`, and `arcs/LOCKS.md`. Also note which other pages import from your paths (e.g. scale-explorer imports composition-workbench): changing exported APIs there is a cross-arc change.
6. A decision that touches shared code or a shared contract (pitch/tuning representation, time, PianoRoll behaviour, theme, desk/edit contract) is appended to `DECISIONS.md` (columns: id, date, arc, decision, why, affects, status, source) in the same milestone.
7. The reviewer has a standing question: did this change touch something another arc reads, is it recorded in `DECISIONS.md`, and are the other consumers updated or logged in `BACKLOG.md`?
8. Same checkout: concurrent arcs run as separate sessions in this one checkout on one branch, so `arcs/LOCKS.md`, `DECISIONS.md`, `BACKLOG.md` and every arc's `PROGRESS.md` are visible to all immediately. Each arc commits only the paths it owns or holds a lock on (path-scoped `git add <paths>` and `git commit -- <paths>`, never `git add -A`, `git add .` or a bare `git commit`: sessions share one index; on an `index.lock` error retry, never delete the lock). `DECISIONS.md` ids are arc-prefixed (e.g. `W-12`, `STAGE-3`). Worktrees stay optional for risky shared work; if one is used, read and write the coordination files only in the main checkout, and copy the gitignored local `.claude/` files into the worktree if you need them (see "Per-checkout files" below).
9. The human decides conflicts.
10. Standing shared paths (always need a lock): `package.json`, `yarn.lock`, `vite.config.mjs`, `src/Router.tsx`, `src/data/applets.ts`, the `src/pages/<Name>.page.tsx` entry files, `src/theme/`, `src/components/` (shared components), the `oxfmt`/`oxlint` configs, `.claude/agents/`, and the `CLAUDE.md` files. The shared coordination docs (`DECISIONS.md`, `BACKLOG.md`, `arcs/LOCKS.md`) need no lock for adding or removing your own rows or items (rule 13). New-arc setup, under a lock on `package.json`: create the arc's `check:<arc>` script before its first code milestone (rule 16).
11. Workstream folders and tags: see Layout. BACKLOG tags are the workstream folder name or `[shared]`.
12. The orchestrator (not the builder) writes `arcs/LOCKS.md` rows and the `PROGRESS.md` "Shared touches" line. After writing a lock row, re-read `arcs/LOCKS.md`: if another arc wrote a row for the same path, the earlier row wins, or the human decides. An abandoned arc's lock is released by the human, or by the orchestrator of the arc that needs the path after the human OKs it. Builders never edit `ARC.md`/`PROGRESS.md` and never commit.
13. Commit timing and locks: each arc's orchestrator commits at the end of every milestone (path-scoped `git add` and `git commit -- <paths>` of its owned paths and the shared paths it holds a lock on; never a bare `git commit`, on an `index.lock` error retry and never delete the lock). A lock row is removed ONLY AFTER that path has been committed. `DECISIONS.md`, `BACKLOG.md` and `arcs/LOCKS.md` need no lock for adding or removing your own rows or items; any session may `git add` them, and another session's rows riding along in someone's commit is accepted.
14. Shared gate: every `check:<arc>` runs the project-wide `tsc --noEmit`, so an unfinished edit by another arc can turn your gate red. If the gate is red only because of files outside your owned and locked paths, or because of an error caused by another arc's change wherever `tsc` reports it (including in your own files), it is not yours to fix: do not rewrite your files to fit someone else's unfinished change; stop, report, and wait for that arc's next commit or the human's decision (workflow rule 3 does not oblige you to repair other arcs' files).
15. New check scripts are created so they can be green before the arc has code: `vitest run --passWithNoTests src/pages/<x>`, stylelint `--allow-empty-input`, and `--no-error-on-unmatched-pattern` on both `oxfmt` and `oxlint` (they exit non-zero on a missing folder otherwise); the template precondition says so.
16. Starting a new arc: the human names the workstream and the goal; the orchestrator creates `arcs/<name>/`, drafts `ARC.md` from the template (Owned/Shared paths, Check command, C0) and the human approves it before C0. Setup order: setup happens right after the human approves `ARC.md` and BEFORE C0: take the `package.json` lock, add `check:<arc>`, named with the full arc folder name and no abbreviation (`check:interval-placement`, not `check:ip`; the older `check:hfl` stays as it is) (the orchestrator may edit `package.json` for this and nothing else), commit (the setup commit includes `arcs/<name>/` and `package.json`), release the lock. Page registration locks (`src/Router.tsx`, `src/data/applets.ts`, the entry file) are taken in the first code milestone. The new page's entry file `src/pages/<Name>.page.tsx` is a standing shared path, not an owned path, even though the arc creates it. `DECISIONS.md` ids use a unique prefix registered in the arc's first row. A new prefix is the arc folder name in capitals with the hyphens dropped (`STAGE` for `stage`, `INTERVALPLACEMENT` for `interval-placement`), never an abbreviation or a single letter: those read as cryptic and run out (human, 2026-11-20). The older single-letter prefixes `W`, `S` and `H` stay as they are. Agents given an arc folder without an `ARC.md` stop and report instead of defaulting. Builders never take locks: if the arc does not already hold a lock the milestone needs, they stop and report.

## Per-checkout files

The root `CLAUDE.md` and `.claude/agents/` (the `builder`, `reviewer` and `scout` definitions in `shell/.claude/agents/`) are tracked, so a fresh clone, a new worktree or a Claude Code on the web session has them. The rest of `.claude/` (`settings.local.json`, `launch.json`, local skills and worktrees) stays gitignored and per checkout; copy those into a new worktree if you need them. Auto-memory (`~/.claude/projects/.../memory`) is also local and is not in the repo. `WORKFLOW_HANDOFF.md` section 5 holds copies of the agent definitions (kept in step with `.claude/agents/*.md`).

## Checks

- Each arc is gated by its own scoped `Check command` from its `ARC.md`. Do not use the repo-wide `yarn test` as a gate: other areas carry unrelated failures.
- Fast loop: `corepack yarn check:fast [files...]` (`scripts/check-fast.mjs`) runs format, lint, stylelint and `vitest related` on only the files changed since HEAD (plus untracked), or on the files you name; `--types` adds the project-wide `tsc`, `--tests-only` skips format and lint. Use it instead of raw `vitest related`: on Windows vitest 4 compares paths to test module ids with `===`, the ids carry the on-disk letter case (`C:/Data Files/Projects/Hrifa`) and this checkout's cwd is lowercase, so plain `vitest related` finds nothing and exits 0. The script resolves casing first. It is not a gate. `related` follows imports through barrels: a shared `src/lib/harmonic-field` file pulls in the heavy lab page suites, so name a narrower test file when you only need a unit test.
- Hard rule (the human has objected twice): after an edit, run ONLY the one test file that covers it, with `corepack yarn vitest <file>` (the `vitest` script is already `vitest run`; `yarn vitest run <file>` becomes `vitest run run <file>`, where the extra `run` is a name filter that pulls in unrelated test files). Never pass a barrel or widely imported file (`texts.ts`, `ui.tsx`, `labState.ts`, any `index.ts`, anything in `src/lib/harmonic-field`) to `check:fast`, `test:related` or `vitest related`: they follow imports into dozens of heavy page suites (one such run was 46 files, 293 s, 3 timeouts). A look-only change (CSS, label, placeholder, help text) needs at most the one test that queries it. Broad runs only when the human asks.
- Test-run policy: while building, builders run only the tests related to their changes (`corepack yarn check:fast <changed source files>`; `test:related` is the same wrapper with `--tests-only`), never the gate. Reviewers do not run the gate or a test folder; they read the diff and may run one targeted test file or test when a claim needs proof. The orchestrator runs the arc's `Check command` once per milestone, before the commit (or once per attempt). Small changes between milestones: related tests only; the gate runs at the next commit. The orchestrator does not repeat the builder's per-file runs (Workflow cost rules, 5). Never run the whole suite after every edit.
- Delegation: builder + reviewer for real milestones (features, persistence, audio, state). The orchestrator does small or look-only changes and short, well-specified review fixes directly. Scout only when the location is unknown.
- Test environments (`vite.config.mjs`, two vitest projects): `*.test.ts` run in plain Node (about 5x faster, no jsdom and no `vitest.setup.mjs`); `*.test.tsx` and the files in `DOM_TESTS` run in jsdom. A new `.test.ts` that needs `window`, `document` or `localStorage` is added to `DOM_TESTS` (or written as `.test.tsx`). Whole-page jsdom renders cost 3 to 9 s each: keep page tests few and give heavy suites their own files so they run in parallel.
- Workbench work is gated by `corepack yarn check:workbench`: `npm run typecheck` (`tsc --noEmit`, NOT scoped: it covers the whole project), then format, lint, stylelint and vitest scoped to `src/pages/composition-workbench` (see rule 14).
- If `corepack` is not on PATH, run `node .yarn/releases/yarn-4.18.0.cjs run check:workbench` from `shell/` (same pattern for another arc's `check:<arc>`).
- Node 25+ breaks jsdom's `localStorage`; `vite.config.mjs` passes `--no-experimental-webstorage` to avoid this. Don't remove it.
- Line endings are LF (`.editorconfig`, `.gitattributes`). Write LF.

## Environment notes (Windows machine)

- `.nvmrc` pins Node 24.18.1. The system Node is 26 (kept for Ghidra, do not replace it). A portable Node 24.18.1 lives at `C:\Users\apoor\tools\node-v24.18.1-win-x64`: before any `corepack yarn` or vitest run in PowerShell, `$env:PATH="$env:USERPROFILE\tools\node-v24.18.1-win-x64;$env:PATH"` and check `node -v`.
- Gate runs: set `VITEST_MAX_WORKERS=6` (`$env:VITEST_MAX_WORKERS="6"`), one worker per physical core (Ryzen 5 5600X: 6 cores, 12 threads, 64 GB). With the default worker count (11) on this machine, 5 to 7 page tests time out at 15 s (different ones each run, all pass alone): jsdom tests are CPU-bound, so more workers than physical cores only fight each other. Measured at 4 workers (2026-11-16, Defender exclusions on `shell/` and the portable Node folder): full vitest run 404 s, 263 files, 3,828 tests, all green; `check:hfl` was 111 s against 130 to 140 s at the default. 6 was chosen on the core count (no gate run for it); a first heavy `check:fast` run at 6 timed out 3 page tests at 15 s (`composites2` x2, `roughness` x1, all pass alone), so those two files now use `vi.setConfig({ testTimeout: 30_000 })` like `HarmonicFieldLab.m8g`. If another page test times out at 6, raise its timeout the same way before going back to 4 workers.
- Quoting: never put code with backslashes, regexes, nested quotes or more than a line or two inline in a shell command (`node -e`, `python -c`, `sed`, `echo >`): the tool, the shell and the interpreter each eat different characters, and it fails with parse errors. Write the code to a script file with the Write tool (the session scratchpad for throwaway scripts) and run `node file.mjs <args>`; pass paths as arguments, not inside the code. Edit repo files with the Edit tool. Multi-line text for a native command (a commit message) in PowerShell is a single-quoted here-string (`@'` ... `'@`, the closing `'@` at column 0). PowerShell 5.1 `Get-Content` and `Set-Content` also corrupt UTF-8: read and write files with the Read, Write and Edit tools.
- `vite.config.mjs` inlines `@testing-library/jest-dom` for the dom project. Without it the matchers (`toBeInTheDocument` ...) do not register and about 126 tests fail with `Invalid Chai property`. Do not remove it.
