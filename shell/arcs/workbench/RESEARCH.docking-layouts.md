# Research: dockable layouts (2026-11-14, for the one-Stage arc)

Condensed from a web research report. Marked **(source)** when read in this session, **(memory)** when from the researcher's background knowledge and NOT verified, **(judgement)** for the researcher's opinion. Several fetches failed (Cockos wiki, Blender docs, rc-dock and Golden Layout pages, one dockview page).

## What established systems do

- **Every library models a layout as a tree.** dockview (nested splits, groups), FlexLayout (rows, tabsets and tabs; child rows alternate orientation; relative weights), i3 (nested containers: splith, splitv, stacking, tabbed) (source). Blender: a binary split tree of areas with minimum sizes (memory). VS Code: editor groups are a nested splitview with orientation and sizes (memory).
- **The human's three target arrangements are all trees of nested splits with leaf dockers**: (a) top over bottom with a right-hand docker of 3 tabs, (b) left, centre, right, (c) a top docker over a bottom that is split left and right. The current "columns of stacked slots" model is a depth-2 tree, so migrating old layouts is lossless (judgement). (a) and (c) need deeper nesting than depth 2.
- **Naming containers:** none of the libraries has first-class user-chosen names. The closest verified precedent is i3 marks (a user-chosen identifier you can target) (source). dockview and FlexLayout give IDs only; a name would be our own field. Keep a stable `id` separate from a mutable `name` (judgement). REAPER: dockers are numbered slots and each window remembers which docker it was in (memory); no source found for renaming a docker.
- **Drag and drop docking:** the common pattern is a drop overlay with a centre zone (join as a tab) and four edge zones (split in that direction), with a translucent preview. Pitfalls (judgement/memory): overlay flicker over canvases and iframes (use a transparent shield while dragging), tiny edge zones on small dockers, no keyboard alternative (hence the "send to docker" menu), dragging within the same container must do nothing, and auto-deleting empty containers conflicts with named persistent dockers.
- **Saved workspaces:** the libraries serialise the whole layout as JSON (dockview `toJSON` and `fromJSON`, FlexLayout's model) (source). A workspace is a named JSON blob plus a switch action; REAPER screensets and Blender workspaces work this way conceptually. Restoring must tolerate unknown or missing panel ids; dockview resets on invalid data (source).
- **Keyboard:** two conventions. Pane-level: F6 and Shift+F6 cycle workbench areas in VS Code; Ctrl+1/2/3 focus editor groups 1 to 3 (source). Within a container: the WAI-ARIA tabs pattern (Tab enters the active tab, Left and Right move between tabs, Home and End optional, manual activation advised unless switching is instant) (source). "Select a docker by shortcut, then cycle its tabs" fits both. Give each docker `role=tablist` and a labelled region (its name) (judgement).
- **Minimum sizes and narrow windows:** not verified for any library. Judgement: each leaf gets a minimum derived from its active panel, the split solver clamps it, and below a threshold collapse to a single docker or a tab strip.
- **Remounting:** React cannot move a rendered subtree between DOM parents without remounting (source: React issue thread). dockview's default render mode removes a hidden panel's DOM (losing scroll position and DOM state); its `always` mode keeps it hidden but alive; re-parenting an iframe reloads it (source). The robust pattern is the one this repo already uses: render each panel once via `createPortal` into a stable detached host node and physically move the host node into whichever docker is active (judgement). Check the canvas and piano roll handle `ResizeObserver` after a move.

## Researcher's recommendation (judgement)

Build a custom split tree with named leaf dockers on top of the existing core and keep the portal-hosted panels, rather than adopt a library. Reasons: the needs (named dockers, send-to-docker, last-docker memory, keyboard docker selection, Mantine theming, mounted-once portals) are mostly domain features that libraries do not provide, and libraries own the DOM structure that decides whether content is re-parented, which fights mounted-once. dockview is the strongest library candidate (React 19 peer dependency, serialisation, floating and popout, ARIA) but has its own DOM and CSS to theme, no naming model, an unverified portal-moves guarantee and a possible portal bug (issue 793); spatial keyboard docking is paid. A spike with dockview is worthwhile only if floating windows or popouts become requirements.

Suggested shape: `Node = split { dir, children: [{ node, weight, min }] } | docker { id, name, tabs: [panelId], active }`; panels live outside the tree, keyed by id; a `lastDocker` map (panel id to docker id) beside it; a workspace is `{ name, tree, lastDocker }` as JSON with a version field and validation on load. Suggested rule: dockers never auto-delete when emptied; only the user removes them (keeps names stable and "send to X" reliable). Cost of building: a drop-overlay component, a splitter solver with minimums, tab-strip keyboard logic and tree edit operations (split, move, close, collapse empty); the existing columns-of-stacks splitters are reusable.
